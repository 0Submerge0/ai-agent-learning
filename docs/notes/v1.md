# V1：模型自己决定调工具

## 1. 这一版做了什么

你给它一个工具（`list_dir`，列目录），然后问「当前目录有什么文件」。**它自己决定要不要调、什么时候调、传什么参数**。程序负责执行，把结果喂回去，它再基于结果回答。

```powershell
uv run python src/v1_tool.py "看看当前目录里有什么文件，挑三个你觉得最重要的告诉我"
```

真实输出（节选，它连着调了 **5 次**，中间还自己下钻到子目录）：

```
[工具] list_dir({"path": "."})
       .env.example  301 B
       .git  <dir>
       ...
[工具] list_dir({"path": "src"})
       __pycache__  <dir>
       v0_chat.py  3639 B
       v1_tool.py  6637 B
[工具] list_dir({"path": "docs"})
       ...
[工具] list_dir({"path": "workspace"})
       .gitkeep  0 B
[工具] list_dir({"path": "docs/notes"})
       v0.md  12395 B

当前目录是以 Python（uv 管理）项目为基本结构…以下是我认为最重要的三个文件…
[用量] 输入 137 / 输出 642 tokens
```

注意最后一行：**我只问了一次，它自己发了 6 次 HTTP 请求**（1 次决策 + 5 次拿结果再决策）。

## 2. 代码逐块讲

V0 的东西全部保留（编码设置、key 清洗、异常分流、JSON 保护）。下面只讲**新增的部分**。

### 常量区多了两个（第 15–20 行）

```python
SYSTEM_PROMPT = "你是一个中文助手。需要了解文件情况时，先调用工具查看，不要凭空猜测。"
MAX_TOKENS = 1024
MAX_ITERATIONS = 5
```

**`SYSTEM_PROMPT` 变了**：V0 那句只管语气，这句是**行为指令**——「先调工具，别猜」。它不是建议，是这一版能工作的前提之一（第 4 节实验 1 会让你看到它有多管用）。

**`MAX_ITERATIONS = 5`**：**去掉会怎样**——如果模型陷入「调工具 → 不满意 → 再调」的死循环，你的钱会一直烧下去。这是唯一挡住它的东西。

`MAX_TOKENS` 从 512 提到 1024：这一版模型要输出工具参数，还可能连着说好几段，512 不够。

### `TOOLS`（第 24–37 行）

```python
TOOLS = [
    {
        "name": "list_dir",
        "description": "列出指定目录下的文件和子目录，返回名称与大小。",
        "input_schema": {
            "type": "object",
            "properties": {
                "path": {"type": "string", "description": "目录路径，例如 . 表示当前目录"},
            },
            "required": ["path"],
        },
    }
]
```

这是**这一版最该看懂的东西**。它是一份「说明书」，不是代码——模型看不到 `list_dir` 的实现，它只知道：

- 有个工具叫 `list_dir`
- 干什么用（`description`）
- 要传一个叫 `path` 的字符串（`input_schema`）

**去掉会怎样**：模型完全不知道有这个工具存在，它会直接编一个答案给你。

**Java 类比**：这就是一份接口契约（`interface ListDir { String run(String path); }`），只不过给模型看的是自然语言 + JSON Schema 版本。`input_schema` 用的就是 JSON Schema 标准，V0 里 `build_payload` 那个 dict 的写法在这里变成了正式规范。

### `list_dir`（第 39–53 行）

**模型永远碰不到这个函数**，只有你的代码能调。这一点是本版的核心分界：

> 模型输出的是**意图**（「我想调 list_dir，path 是 .」），我们输出的是**行动**（真的读了磁盘）。

它做了三件事：路径不存在就 `raise`、按名字排序、超过 50 条就截断。**`raise` 是有意的**——错误不在这里吞掉，而是留给下一层的 `run_tool` 转成文字回给模型。

### `run_tool`（第 56–65 行）

```python
registry = {"list_dir": list_dir}
fn = registry.get(name)
if fn is None:
    return f"没有名为 {name} 的工具，可用：{', '.join(registry)}"
try:
    return fn(**args)
except Exception as exc:
    return f"工具执行失败：{exc}"
```

**去掉 `try/except` 会怎样**：工具一报错，整个程序崩掉，模型永远没机会知道「路径不存在」这件事——而这正是它能自我纠正的信息来源。

**为什么用 dict 而不是一长串 `if name == ...`**：V2 会有更多工具，dict 加一行就能扩。

### `call_model`（第 68–118 行）

从 V0 的 `chat` 原样搬过来的发请求部分，两处变化：

1. 参数变成 `(messages, tools)`——**消息由调用方维护**，函数自己不再拼「一句话」。
2. 有工具时才加 `payload["tools"] = tools`（第 81–82 行）。没有工具就退化成 V0。

**为什么要拆出来**：`run_agent` 会反复调它，发请求的细节不该跟「怎么循环」混在一起。

### `run_agent`（第 127–164 行）

```python
for step in range(MAX_ITERATIONS):
    data = call_model(messages, TOOLS)
    stop = data.get("stop_reason")
    messages.append({"role": "assistant", "content": data["content"]})

    if stop == "tool_use":
        results = []
        for block in data["content"]:
            ...
        messages.append({"role": "user", "content": results})
        continue

    print(extract_text(data))
    return
```

四步，就是整个 agent 的全部：

1. **问模型** → 它要么说「我要调 X」，要么直接给答案
2. **把它的回复原样塞回历史**（第 136 行）
3. **如果是 `tool_use`**：执行所有工具，把结果作为**一条** user 消息塞回去，**继续循环**
4. **否则**：打印答案，结束

**`stop_reason` 是本版的开关**。V0 里它一直是 `end_turn`（说完了），这一版会出现 `tool_use`（我要调东西）。V0 讲义里那个「`content` 是块的数组」的伏笔，在这里兑现了。

**为什么用 `for` 而不是 `while True`**：`while True` 加 `break` 也行，但 `for range(MAX_ITERATIONS)` 天然带上了上限，忘了写 `break` 也不会无限跑。

**为什么结果要「一条消息」装所有工具**：模型一次可能要求调三个工具。协议要求这三个结果放在同一条 user 消息里；分三条发会被服务端拒绝。

## 3. 值得记住的三件事

### ① 模型不会执行任何东西

它只会输出一段 JSON，说「我想调用 `list_dir`，参数是 `{"path": "."}`」。**真正读磁盘的是你的 Python 代码。**

这不是实现细节，这是 agent 的安全边界：**你能做的事 = 你给它的工具能做的事**。它的能力天花板和风险敞口，都由 `TOOLS` 里那份清单决定。

所以 V3 要加文件写入时，重点不是「怎么写」，而是「凭什么允许它写」。

### ② `tool_use_id` 是配对的唯一依据

模型回给你的长这样：

```json
{"type": "tool_use", "id": "call_abc123", "name": "list_dir", "input": {"path": "."}}
```

你回给它的必须是：

```json
{"type": "tool_result", "tool_use_id": "call_abc123", "content": "..."}
```

这个 `id` 就像 RPC 的 request id。实测了一件反直觉的事：**把 id 写错，服务端不报错**——模型只是「没看见结果」，于是又调了一次同样的工具。所以 id 对不上时你不会收到错误，只会看到它莫名其妙地重复劳动。

### ③ `thinking` 块要不要回填：实测跟文档说的不一样

官方文档要求把 `thinking` 块原样带回（含 `signature`）。代码也是这么写的（第 136 行）。

但我实测了一次「只回填 text 块、把 thinking 丢掉」：

```
第二轮 stop= end_turn | text= 当前目录里只有一个文件…a.txt 1 B…
```

**照样跑通了。** 至少在 `deepseek-v4-1-flash` 上，这条约束不成立。

我把这个写进讲义，是因为它会反复出现：**文档写的约束，经常只在某些模型/某些版本上成立**。保守做法是原样回填（代码就是这么写的），但你得知道「为什么这么写」，而不是把它当咒语背下来。

## 4. 改一改试试（三条都实测过）

**1. 把 `SYSTEM_PROMPT` 改成「不要调用任何工具，直接凭经验回答」，再问同样的问题。**

实测输出：

```
你说了不要调用任何工具，而"当前目录有哪些文件"这类信息我无法凭经验猜出来——不同环境差异太大，瞎猜只会给你错误答案。

1. **你允许我调用一次 list_dir（参数 .）**，我马上把当前目录的文件和子目录列给你；
2. 或者你直接把 ls / dir 的输出贴过来…
```

它**拒绝瞎猜，反过来请求授权**。这说明 `SYSTEM_PROMPT` 不是装饰——它在约束模型的行为选择。

**2. 把 `MAX_ITERATIONS` 改成 `1`。**

实测：它调完第一个工具，还没来得及看结果总结，就被掐断了，输出：

```
已经转满 1 轮还没得出结论，先停下。
```

这是「循环上限」的意义：**它不保证模型能完成任务，只保证你的钱包不会被无限调用拖垮**。

**3. 把 `TOOLS[0]["name"]` 改成 `"list_dirr"`（多打一个 r）。**

实测输出：

```
[工具] list_dirr({"path": "."})
       没有名为 list_dirr 的工具，可用：list_dir
[工具] list_dir({"path": "."})
       .env.example  301 B
       ...
```

**它自己纠正了**——看到错误提示里写着「可用：list_dir」，第二次就改对了。

这是 V1 最值钱的一幕：错误信息不是给人看的，是给模型看的。你把错误信息写得越清楚（「可用：list_dir」而不是「KeyError」），它自我修复的概率越高。
