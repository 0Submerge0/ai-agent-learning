# V3：文件整理、沙箱与「人把关」

## 1. 这一版做了什么

从「能聊、能看目录」升级到「**能真的改文件**」：新增 `read_file`（读文件）、`mkdir`（建目录）、`move_file`（移动/改名）。同时上了两道 V1/V2 完全没有的闸门：

1. **沙箱**：所有文件操作只能发生在 `workspace\` 之内，越界直接拒绝。
2. **写操作确认**：`mkdir` / `move_file` 先打印计划，用户输入 `y` 才执行。

真实运行（先让它整理图片）：

```
V3 文件整理助手。只能操作 workspace。写操作会让你确认 (y/N)。输入 /clear 清空记忆，/exit 退出。
你> 把 workspace 里的图片文件（.jpg）都移动到 images 目录，先建目录再移动。
[工具] list_dir({"path": "."})
       .gitkeep  0 B
       发票1.jpg  10 B
       发票2.jpg  10 B
       报销单.txt  59 B
       旧笔记.txt  26 B
助手> 我在 workspace 根目录找到这些文件：…目前没有 images 目录，需要新建。

## 执行计划

1. 新建目录 `images/`
2. 移动 `发票1.jpg` → `images/发票1.jpg`
3. 移动 `发票2.jpg` → `images/发票2.jpg`

确认请回复 y，我再实际执行。

[用量] 本次输入 99 / 输出 222 tokens
你> y
[工具] mkdir({"path": "images"})
[计划] 创建目录 workspace/images
执行? (y/N) y
       已创建目录 images
[工具] move_file({"src": "发票1.jpg", "dst": "images/发票1.jpg"})
[计划] 移动 workspace/发票1.jpg → workspace/images/发票1.jpg
执行? (y/N) y
       已移动 发票1.jpg → images/发票1.jpg
[工具] move_file({"src": "发票2.jpg", "dst": "images/发票2.jpg"})
[计划] 移动 workspace/发票2.jpg → workspace/images/发票2.jpg
执行? (y/N) y
       已移动 发票2.jpg → images/发票2.jpg
[工具] list_dir({"path": "images"})
       images/发票1.jpg  10 B
       images/发票2.jpg  10 B
助手> 完成。已核对结果：…两个 .jpg 都已移入，其余文件未改动。

[用量] 本次输入 216 / 输出 73 tokens
```

注意这里其实有**两层把关**，别混为一谈：

- 第一层是**模型自己**：它先列计划、问「确认请回复 y」，才去调工具。这是 `SYSTEM_PROMPT` 教出来的，属于「软约束」——它可能哪天就不问了。
- 第二层是**你的代码**：每次 `mkdir` / `move_file` 前面那行 `执行? (y/N)`。这是「硬约束」——不管模型多想执行，代码不收到 `y` 就不动手。

这一版真正值钱的不是「能移动文件」，而是**这两层防护分别由谁负责**。

## 2. 代码逐块讲

### 2.1 为什么这一版要拆包

V2 是单文件 201 行，还能顺着读。V3 要再加 4 个工具、沙箱、计划描述，全塞一个文件会接近 300 行，而且三类职责混在一起：

- **和模型通信**（发请求、重试、解析响应）
- **工具**（定义、实现、分发、确认）
- **路径安全**（沙箱）

所以拆成 `src\agent\` 包：

```
src\
  agent\
    __init__.py
    client.py    # 和模型通信（V2 的 call_model 搬进来）
    tools.py     # 4 个工具 + 分发 + 确认
    sandbox.py   # 路径校验
  v3_files.py    # 入口：REPL + 工具循环
```

**Java 类比**：`agent\` 就是一个 package，`from agent.tools import ...` 就是 `import`。包内部用相对导入 `from .sandbox import ...`（`.sandbox` 表示「同一个包里的 sandbox」）。

这是整个课程里最重要的一次「抽象」：**不是提前设计的，是被需求逼出来的**。V1/V2 单文件更利于并排对照，V3 再加东西就失控了，拆包才有意义。

### 2.2 `sandbox.py`：越界的唯一防线（29 行）

```python
# 第 5–6 行
WORKSPACE = Path(__file__).resolve().parent.parent.parent / "workspace"
```

用**相对本文件自身**的方式定位 workspace，而不是写死 `D:\zjy\AI\workspace`。换机器、换目录都不会失效。

核心是 `safe_path`（第 9–21 行）：

```python
def safe_path(path: str, must_exist: bool = False) -> Path:
    base = WORKSPACE.resolve()
    p = Path(path)
    target = (p if p.is_absolute() else base / p).resolve()
    if not target.is_relative_to(base):
        raise ValueError(f"路径越界，只允许操作 workspace 之内：{path}")
    if must_exist and not target.exists():
        raise ValueError(f"路径不存在：{path}")
    return target
```

三个关键点：

1. **相对路径按 workspace 解释**（第 16 行）。所以同一个工具调用 `{"path": "."}`，V2 里表示项目根目录 `D:\zjy\AI`，V3 里表示 `D:\zjy\AI\workspace`——**沙箱重新定义了「.」的含义**。模型并不知道这件事，它只是拿到一份不同的目录列表。
2. **先 `resolve()` 再检查**（第 16–17 行）。`resolve()` 会把 `..` 折回真实位置、把符号链接展开，所以 `../src`、`D:\zjy\AI\workspace\..\src`、workspace 内指向外部的软链接，最后都会落到 `D:\zjy\AI\src`，被 `is_relative_to` 拦下。
3. **越界直接 `raise`**（第 18 行）。异常会被 `run_tool` 捕获、转成文字回给模型；模型据此知道「这条路走不通」。

实测（直接调工具，不经过模型）：

```
../src -> 工具执行失败：路径越界，只允许操作 workspace 之内：../src
D:/zjy/AI/src/v2_repl.py -> 工具执行失败：路径越界，只允许操作 workspace 之内：D:/zjy/AI/src/v2_repl.py
D:/zjy/AI/workspace/../src -> 工具执行失败：路径越界，只允许操作 workspace 之内：D:/zjy/AI/workspace/../src
```

`rel()`（第 24–29 行）只是把绝对路径转成 `images/发票1.jpg` 这种给人看的显示形式。

### 2.3 `tools.py`：工具、写操作清单与确认闸门（129 行）

**4 个工具的定义**（第 5–51 行）和 V1 的结构完全一样，只是多了三个。`description` 里明确写了「这是写操作，需要用户确认」——这句话是给模型看的，让它别把写操作当成随手可做的事。

**`WRITE_TOOLS`（第 53 行）是最该盯住的一行**：

```python
WRITE_TOOLS = {"mkdir", "move_file"}
```

它就是「哪些工具需要人确认」的**唯一清单**。加一个新的危险工具，只要把名字扔进这个集合，确认闸门自动生效。**这个集合就是你的权限模型。**

四个工具函数都很短：

- `list_dir`（第 56–67 行）：列目录，最多 50 条。
- `read_file`（第 70–77 行）：读 UTF-8 文本，超过 4000 字符截断。
- `mkdir`（第 80–85 行）：已存在则 `raise`。
- `move_file`（第 88–95 行）：源必须存在、**目标已存在则拒绝覆盖**、父目录自动创建。

**每个函数第一句都是 `safe_path(...)`**——这是「安全靠代码强制」的写法：不管谁调用，先过沙箱。

**确认闸门在 `run_tool` 里**（第 106–129 行），核心是第 117–127 行：

```python
try:
    if name in WRITE_TOOLS:
        print(f"[计划] {describe_write(name, args)}")
        ask = ask or input
        try:
            answer = ask("执行? (y/N) ")
        except EOFError:
            answer = ""
        if answer.strip().lower() != "y":
            return "用户拒绝了这次操作，未执行。"
    return fn(**args)
except Exception as exc:
    return f"工具执行失败：{exc}"
```

**顺序很重要**：先打印计划（dry-run），再问，只有 `y` 才真正调函数。用户答 `n`、直接回车、或者管道结束（`EOFError`）——统统不执行。

还有一个细节：`ask = ask or input`（第 120 行）。默认用 `input()` 问真人；测试时可以注入一个假的 `ask` 函数，不用真敲键盘。**这就是「依赖可替换」的雏形**，V4 做测试时会再见到。

### 2.4 `client.py`：从 V2 搬来的通信层（71 行）

逻辑和 V2 的 `call_model` 一模一样（重试、打码、HTTP 错误、JSON 保护），只有一处变化：

```python
def call_model(messages: list, tools: list, system: str, retries: int = 2) -> dict:
```

`system` 从模块常量变成了**参数**（第 17 行）。理由：提示词是「这一版助手的行为」，不是「通信协议」的一部分。`client.py` 只负责把话说出去、把话收回来，不该知道你是聊天助手还是文件助手。

### 2.5 `v3_files.py`：入口，和 V2 几乎一样（91 行）

- 第 6–7 行：从包里导入 `ModelError / call_model / extract_text` 和 `TOOLS / run_tool`。
- 第 17–21 行：`SYSTEM_PROMPT` 改成文件助手的行为指令，明确「只能操作 workspace」「写前先说计划」。
- 第 22 行：`MAX_ITERATIONS = 8`（V1/V2 是 5）。整理文件是多步操作（建目录 + 移动多个文件 + 复查），5 轮可能不够。
- 第 25–61 行 `run_turn`：和 V2 逐行相同——工具循环、原样回填、结果进历史。第 41 行把 `run_tool` 从包里调过来。
- 第 64–87 行 `run_repl`：`/clear`、`/exit`、`ModelError` 捕获、UTF-8 修复，全部保留。

**这一版没有改工具循环**。V1 学会的那套「问模型 → 执行 → 回喂 → 再问」原样复用，只是工具从 1 个变成 4 个。这说明一件事：**agent 的骨架很小，能力增长主要靠往 `TOOLS` 里加东西。**

## 3. 值得记住的三件事

### ① 沙箱是「能力的边界」，不是「代码的礼貌」

模型能做什么，**完全等于**你给它的工具能做什么。V2 的 `list_dir` 没有沙箱，它能列出整个 `D:\`；V3 的 `list_dir` 第一句就是 `safe_path`，它只能看到 `workspace`。

这不是「我们请求模型别乱来」，而是「**即使模型乱来，代码也做不成**」。区别在于：前者靠模型自觉，后者靠 `raise`。

> Java 类比：这不是「接口文档里写一句请勿传负数」，而是方法第一行 `if (n < 0) throw new IllegalArgumentException()`。

实测里模型主动说了「路径在工作区之外，我无法读取」——那是它读懂了错误信息后的**礼貌**。真正的保险是 `safe_path` 第 17 行那句 `raise`，模型态度好不好都不影响它。

### ② 写操作必须有人把关（human-in-the-loop）

模型可以**提议**，但不能**单方面执行**。`run_tool` 里的 `if name in WRITE_TOOLS` 就是那道开关：

- 模型说「我要建 `archive` 目录」→ 代码打印计划 → 问 `y/N` → 你说 `n` → 返回「用户拒绝了这次操作，未执行」。
- 实测：

```
[工具] mkdir({"path": "archive"})
[计划] 创建目录 workspace/archive
执行? (y/N) n
       用户拒绝了这次操作，未执行。
助手> `archive` 目录的创建操作被拒绝了，所以文件还没有移动。
我没有继续执行任何操作，报销单.txt 仍在根目录，archive 也未创建。
```

注意模型的反应：它没有崩，也没有偷偷换个方式再试，而是**如实汇报「被拒绝了」并等你下一步指示**。这就是「拒绝」该有的样子——不是报错，而是一个模型能读懂的结果。

为什么写操作要单独把关，读操作不用？因为**读错了只是看到不该看的东西，写错了是不可逆的**。移动/覆盖/删除会让文件消失，模型再聪明也没法把删掉的文件变回来。所以「不可逆操作」必须留一个人按开关。

### ③ 抽象是被需求逼出来的

V2 单文件 201 行，读起来还顺；V3 如果继续单文件，会变成 4 个工具 + 沙箱 + 确认 + 通信，接近 300 行，三类职责搅在一起。这时候拆包不是「为了好看」，而是**再不拆就看不清哪段在干什么了**。

拆完之后每个文件只回答一个问题：

| 文件 | 只回答一个问题 |
|---|---|
| `client.py` | 怎么和模型说话？ |
| `tools.py` | 模型能做什么？哪些要人确认？ |
| `sandbox.py` | 哪些路径允许碰？ |
| `v3_files.py` | 一轮对话怎么转起来？ |

**这就是「抽象」的正确时机**：先让它重复、让它变长，等到痛了再拆。V1/V2 刻意不拆，就是为了让你看到「痛」在哪里。

## 4. 改一改试试（三条都实测过）

**1. 把 `WRITE_TOOLS` 清空，确认闸门立刻消失。**

把 `tools.py` 第 53 行临时改成 `WRITE_TOOLS = set()`，然后用一个「永远回答 n」的 `ask` 调 `mkdir`：

```

改成空集合后，用 ask=lambda _: 'n' 调 mkdir：
已创建目录 noask

```

**明明回答了 `n`，目录还是被建了**——因为 `run_tool` 根本没进确认分支。这说明那道 `y/N` 不是模型的自觉，而是 `WRITE_TOOLS` 这个集合 + 第 118 行 `if` 共同造成的。改完记得改回去。

**2. 去掉 `is_relative_to` 检查，越界立刻能读。**

把 `sandbox.py` 第 17–18 行临时去掉（或用 monkeypatch 模拟），再读 `../src/v2_repl.py`：

