# L4 详解：Agent 架构与状态

> 这是整个项目最值钱的一层，也是最容易被面试深挖的地方。
> 前 8 节讲「架构是什么」，后 4 节讲「成熟产品怎么做、你的项目哪里对哪里错」。

---

# 0. 先定义：什么算 agent，什么不算

## 一句话

> **agent = 一个循环，循环的次数和下一步做什么，由模型运行时的输出决定。**

## 判定标准（三条同时成立）

| # | 条件 | 反例 |
|---|---|---|
| 1 | 模型能**触发副作用**（调工具、改世界） | 纯聊天机器人 → 不是 agent |
| 2 | 模型能看到副作用的**结果**，并据此改变下一步 | 一次性函数调用 → 是 tool use，不是 agent |
| 3 | 循环**次数不确定**，由模型决定何时停 | 固定 DAG 流水线 → 是 workflow |

## 所以这三种都不是 agent

| 形态 | 为什么不是 |
|---|---|
| **单次调用 + 单次工具** | 没有「结果回填后再决策」，条件 2 不成立 |
| **固定 DAG / pipeline** | 步数和路径写死在代码里，条件 3 不成立 |
| **纯 prompt chain** | 没有副作用，条件 1 不成立 |

> 第三种在业界有个专门名字：**agentic workflow**（代理化工作流）。它比 agent 更可控、更便宜，很多生产系统故意选它。
> **面试加分点**：不要把所有 LLM 应用都叫 agent。

# 1. 循环的解剖：六个要素

任何一个 agent 都逃不掉这六个零件。用 `src/v1_tool.py` 的 `run_agent()` 对照：

| # | 要素 | 一句话 | V1 的代码 |
|---|---|---|---|
| 1 | **初始状态** | 循环开始时手上有什么 | `messages = [{"role":"user",...}]` |
| 2 | **调用** | 把状态发给模型 | `data = call_model(messages, TOOLS)` |
| 3 | **判定** | 模型想干什么 | `stop = data.get("stop_reason")` |
| 4 | **副作用** | 真正改变世界 | `output = run_tool(block["name"], args)` |
| 5 | **回填** | 把结果写回状态 | `messages.append({"role":"assistant",...})` / `{"role":"user","content":results}` |
| 6 | **终止** | 什么时候停 | 三类，见下 |

**去掉任何一个，就不是 agent 了**：

- 去掉 4 → 纯对话
- 去掉 5 → 模型看不到结果，无法纠错，第二步开始胡说
- 去掉 6 → 无限花钱

# 2. 终止条件的三个来源

这是设计 agent 时第一个要想清楚的事。

| 来源 | 判据 | 代价 | 落在哪 |
|---|---|---|---|
| **模型自己停** | `stop_reason != "tool_use"` | 正常出口 | `v1_tool.py` ④ |
| **轮次上限** | `for _ in range(MAX_ITERATIONS)` | 可能截断在半路 | V1=5 / V3=8 / V4=16 / V6 动态 |
| **预算上限** | `budget.used >= budget.max_tokens` | 可能截断在半路 | `budget.py` |

## 为什么必须有后两个

因为**模型没有「花费」这个概念**。它不知道自己转了多少轮、花了多少 token。你不设上限，它可以一直调工具。

实测过极端情况：让它列目录，它会 `list_dir .` → `list_dir ./src` → `list_dir ./src/agent`…… 一层层下去，永远不收敛。

## 三种终止的性质完全不同

| | 是「成功」还是「失败」 |
|---|---|
| 模型自己停 | **可能成功也可能失败**（它可能说「我做不到」） |
| 轮次上限 | 一定是「没做完」 |
| 预算上限 | 一定是「没做完」 |

**关键陷阱**：这三者你都只能**观察到**，不能**保证**任务完成。

> 这就是为什么 V5 要引入 `plan.is_complete` ——**把「完成」从「模型说了算」变成「代码算了算」**。
> 这是整个项目最重要的一次质变。

# 3. 控制流演化：V0 → V6

## V0：没有循环

```
一次请求 ──► 一次响应 ──► 打印 ──► 进程退出
```

## V1/V2：单一循环（用户驱动）

```
┌──────────────────────────────────────┐
│  用户说一句                           │
│     ↓                                │
│  ┌─────────────────────────────┐     │
│  │ 调模型                       │     │
│  │   ↓                          │     │
│  │ 要工具？── 是 ──► 执行 ──┐    │     │
│  │   │否                    │    │     │
│  │   ▼                      └────┘     │
│  │ 打印回答                            │
│  └─────────────────────────────┘     │
│     ↓                                │
│  回到等下一句                         │
└──────────────────────────────────────┘
```

**特征**：用户说一句，跑一轮，停下。**循环的驱动源是「用户输入」。**

## V3/V4：同样的循环，加了两个控制面

```
              ┌─── 预算检查（每轮开头）
              │
   循环 ──────┼─── 日志（每步落一条）
              │
              └─── 确认闸门（写操作时暂停等人）
```

**循环本身一行没改。** 加的都是横切面。

## V5/V6：两层循环

```
┌──────────────────────────────────────────────────┐
│ 外层：REPL（等你输入）                             │
│    ↓ 你说「整理 workspace」                        │
│  ┌────────────────────────────────────────────┐  │
│  │ 阶段一：规划循环（最多 6 轮）                │  │
│  │   只读工具 + create_plan                    │  │
│  └────────────────────────────────────────────┘  │
│    ↓ 拿到计划，落盘，问 y/N                       │
│  ┌────────────────────────────────────────────┐  │
│  │ 阶段二：执行循环（16~40 轮）                 │  │
│  │   6 个读写工具 + update_task                │  │
│  │   每轮重渲染计划进 system                    │  │
│  │   退出条件：计划收口 / 预算 / 轮次 / 软着陆   │  │
│  └────────────────────────────────────────────┘  │
│    ↓                                             │
│  回到外层                                        │
└──────────────────────────────────────────────────┘
```

**特征**：**循环的驱动源从「用户输入」变成了「计划里还剩几个 pending」。**

这是 V5 和 V4 的分界线。代码上是这一句（`v5_planner.py` 的 `execution_prompt`）：

```python
"4) 只要计划里还有 pending / in_progress 的任务，就继续调用工具推进，"
"不要停在半路等用户说话；"
```

**没有这一句，V5 就退化回 V4。**

## 一句话总结演化

| 版本 | 驱动源 | 一次授权能干多少 |
|---|---|---|
| V0 | 无循环 | — |
| V1/V2 | 用户一句话 | 最多 5 次模型调用 |
| V3/V4 | 用户一句话 | 最多 8/16 次 |
| V5 | **计划** | 一次 `y` → 7 个任务 → 16+ 次调用 |
| V6 | 计划 + 人工干预 | 同上，但中途可改计划 |

# 4. 五组核心矛盾

架构设计不是「选最好的」，是「在矛盾里选一个平衡点」。这五组你能讲清，面试就稳了。

## 矛盾一：能力 vs 安全

| 想让它更能干 | 代价 |
|---|---|
| 多给工具 | 危险面变大 |
| 工具能写 | 需要确认闸门 → 打断流程 |
| 路径不限制 | 能改系统文件 |

**本项目的选择**：工具只碰 `workspace/`，写操作逐个确认。

**关键洞察**：这不是「提示词里说别乱来」，是 `registry` + `safe_path` 两层代码强制。**提示词是建议，代码是约束。**

## 矛盾二：自主 vs 可控

| 更自主 | 更可控 |
|---|---|
| 一次授权，连续执行 7 个任务 | 每步都停下问 |
| 效率高、体验好 | 你能随时刹车 |
| 出错时已经改了一堆文件 | 出错时最多改一个 |

**本项目的选择**：**分层**——方向上一次批准（计划），每一步上逐个确认（写操作）。

> 这就是「两道闸门」的理论依据：**不同粒度的控制，解决不同粒度的风险。**
> 合成一道会同时失去两者：合成粗的，你批准完就失控；合成细的，你按 7 次 y 也不知道整体对不对。

## 矛盾三：状态 vs 对话

这是 V6 的核心发现，也是最反直觉的一条。

```
模型能看见的：     messages（历史）
你的代码能看见的：  messages + plan + budget（内存对象）
```

**两者会不一致。** 因为：

- `plan` / `budget` 是内存对象，改它们**不会**产生任何消息
- 模型只能读 `messages`

具体例子（V6 实录）：

```
你做的事：                       代码的状态：        模型看到的历史：
/skip 6                         task6 = skipped      （什么都没变）
/retry 4                        task4 = pending      （什么都没变）
调大预算                          remaining = 57000    tool_result: "预算已用完，工具未执行"
/go                             开始执行              模型：「我干不了」×3
```

**模型罢工的原因不是它笨，是它对世界的认知停在旧版本。**

**结论（比修复方案更重要）**：

> **任何「内存里改了状态」的操作，都必须同时产生一条消息，否则模型看不见。**

这条原则适用于所有 agent，不只这个项目。你做服务化、做多 agent、做任何有外部状态的系统，都会撞上它。

## 矛盾四：便宜 vs 完整

| 想省钱 | 代价 |
|---|---|
| 历史裁剪 | 模型忘记做过什么 |
| 摘要压缩 | 丢细节 |
| 少发工具 schema | 它不会用 |
| 短 `max_tokens` | 回答被截断 |

**本项目的选择**：不裁剪（`messages` 只增不减）。**这是它的真实缺陷**，V6 演示 15 条消息就 5.7 万 token。

**为什么这是缺陷而不是设计**：因为「越用越贵」是线性恶化，最终会撞预算然后半路停下。

## 矛盾五：灵活 vs 可测

| 更灵活 | 更可测 |
|---|---|
| 模型自由发挥，能应付意外 | 每次输出不同，没法断言 |
| 提示词随场景调整 | 改了不知道变好还是变坏 |

**本项目的选择**：**没解决**。这就是「面试第 8 题答不了」的原因。

**标准答案**：固定任务集 + 自动断言 + 通过率对比。见学习计划阶段 4.2。

# 5. 记忆的四层（回答「记忆是不是都靠 messages 重发」）

## 结论先说

**短期记忆：是，几乎所有 agent 都靠 messages 重发。**
**但成熟 agent 在它之上还叠了三层。**

## 四层模型

| 层 | 名字 | 载体 | 谁在用 |
|---|---|---|---|
| L1 | **工作记忆** | `messages` 数组，每轮全量重发 | **所有 agent**，包括本项目 |
| L2 | **压缩记忆** | 把旧 messages 摘要成一条，仍在 messages 里 | Claude Code 的 `/compact`、多数长任务 agent |
| L3 | **外部记忆** | 文件 / DB / 向量库，按需检索后注入 | CLAUDE.md、AGENTS.md、`.clinerules`、RAG、MemGPT/Letta |
| L4 | **参数记忆** | 模型权重本身（预训练 + 微调） | 所有模型 |

## L1 为什么是「所有 agent」

因为**模型服务端无状态**。API 每次请求都是独立的，不会有任何「上一次对话」的残留。

所以「记住上一句」这件事，物理上只能靠**你把它再发一遍**。

```
第 1 轮发：[用户:我叫阿杰]
第 2 轮发：[用户:我叫阿杰, 助手:你好阿杰, 用户:我叫什么?]
第 3 轮发：[用户:我叫阿杰, 助手:你好阿杰, 用户:我叫什么?, 助手:你叫阿杰, 用户:...]
```

**这就是「记忆」的全部秘密。** 也是为什么越聊越贵。

## L2 压缩记忆：解决 L1 的线性恶化

当 messages 太长，做两件事之一：

1. **滑动窗口**：只保留最近 N 轮，丢掉最早的
2. **摘要**：用一次模型调用把早期历史压成一段话

Claude Code 的 `/compact` 就是第 2 种：把前面的对话总结成摘要，替换掉原始消息。

**代价**：摘要会丢细节。如果模型需要「第 3 轮那个文件的确切名字」，摘要里可能没有。

**这就是本项目的阶段 3 选项 A**——真实缺陷，值得补。

## L3 外部记忆：解决「记不下」和「跨会话」

三种形态：

| 形态 | 例子 | 特点 |
|---|---|---|
| **约定文件** | `CLAUDE.md`、`AGENTS.md`、`.clinerules` | 每轮注入，人可编辑，模型只读 |
| **检索** | RAG、向量库 | 按 query 找相关片段，省 token |
| **自主记忆工具** | MemGPT/Letta 的 `remember`/`recall` | 模型自己决定写什么进长期记忆 |

第三种最像「真正的记忆」：模型有工具可以主动写一条进长期存储，下次会话再检索出来。

**本项目的对应物**：`sessions/*.json` 是**跨进程**的外部记忆（但只服务于「恢复同一次任务」，不是「跨任务记住你的偏好」）。

## L4 参数记忆：不在「记忆系统」范畴

模型的常识、语言能力、代码知识，都在权重里。这不是你说的「记忆」，但影响了「它记得什么」。

**微调** 是改这一层。本项目没做。

## 还有一种「托管会话」

有些厂商提供**服务端帮你存对话**的接口（比如 Responses API 的 `previous_response_id`、Assistants 的 thread）。

**这不是第五层记忆**，本质还是 L1：只不过「重发 messages」这件事由服务端代劳了。好处是你不用自己存，坏处是你失去了对上下文的完全控制（不能精确裁剪）。

> **面试答法**：
> 「短期记忆靠 messages 重发，因为模型 API 无状态。成熟 agent 在此之上叠两层：压缩（摘要/滑动窗口）和外部存储（约定文件/RAG/记忆工具）。本项目只做了 L1，所以上下文只增不减，这是已知缺陷。」

# 6. 状态管理：三份数据，一个陷阱

## 三份数据

| 数据 | 载体 | 谁改 | 谁能看见 |
|---|---|---|---|
| `messages` | 列表 | 循环每一步 append | **模型**（发过去） |
| `plan` | `Plan` 对象 | `update_task` / 人工命令 | 模型（每轮 render 进 system） |
| `budget` | `Budget` 对象 | `budget.add()` | 模型**看不见** |

## 陷阱：plan 和 messages 的同步是「你负责」的

因为 `plan.render()` 每轮进 system（`execution_prompt`），所以 **plan 的改动对模型是可见的**——这是 V5 做对的一点。

但 `budget` **没有对应的渲染**。它只在预算耗尽时通过一条 `tool_result` 间接暴露给模型：

```python
messages.append({"role": "user", "content": [{
    "type": "tool_result",
    "tool_use_id": b["id"],
    "content": "会话预算已用完，工具未执行。",   # ← 唯一的暴露点
}]})
```

**这条消息是「一次性事实」，但会永久留在历史里。** 预算恢复后，它变成了**过期事实**。

## 修法有两种

| 方案 | 做法 | 代价 |
|---|---|---|
| **改历史** | 把那条旧 `tool_result` 删掉或改写 | 破坏「历史只增」的假设；可能让 `tool_use` 失去配对 |
| **加新事实** | 补一条 user 消息说「那条过期了」 | 多花一点 token，但历史保持合法 |

**V6 选了第二种**（`takeover_message`）。这是**正确选择**，因为第一种会破坏配对约束。

> **抽象成一条原则**：
> **当「历史里的旧结论」与「现在的真实状态」冲突时，不要删历史，要在历史末尾加一条覆盖性的新事实。**
> 这和 git 用 revert 而不是改写历史，是同一个思路。

# 7. 恢复：为什么能，以及准不准

## 为什么能恢复（机制）

因为模型无状态。**只要四样东西齐全，模型看到的世界和退出前一样**：

```
goal       用户原话
phase      停在哪一步
plan       计划 + 每个任务状态
messages   完整历史
budget     花了多少
```

`session_store.save()` 存这六项，`load_resume()` 读回来。

## 恢复得「准不准」是另一回事

V5 只解决「能恢复」，没解决「恢复后知道该干嘛」。

具体问题：`in_progress`。

```
存档里：  3. [in_progress] 把文件按类型移动
messages：... [已移动 a.jpg] [已移动 b.jpg]    ← 做了 2/6
```

恢复后模型面对的模糊：

- 规则 1 说「**开始**任务时设 in_progress」→ 它已经 in_progress 了，所以不触发
- 规则 4 说「有 in_progress 就继续推进」→ 推进到哪？
- `in_progress` 这个标签**不携带进度信息**

三种可能的行为，全是坏的：

| 行为 | 后果 |
|---|---|
| 重做整个任务 3 | 重复移动（好在 `move_file` 拒绝覆盖，会报错） |
| 认为「有人在跑，我不插手」 | 卡住 |
| 从历史推断做到哪了 | **这是唯一正确的，但它靠的是 messages 不是 plan** |

**V6 的 `/retry` 是解药**：把 `in_progress` 打回 `pending`，让状态从「模糊」变成「明确未开始」。

> **原则**：**状态机的每个状态都应该有明确的「下一步动作」。**
> `in_progress` 违反了这条——它表示「正在进行」，但不告诉你「从哪继续」。

# 8. 闸门设计：几道、放哪、代价

## 三道可能的位置

| 位置 | 名字 | 拦什么 | 本项目 |
|---|---|---|---|
| **事前** | 计划审批 | 方向对不对 | ✅ `approve_plan` |
| **事中** | 写操作确认 | 这一步要不要做 | ✅ `WRITE_TOOLS` |
| **事后** | 结果复查 | 做得对不对 | ⚠️ 只在提示词里要求模型自查 |

## 每道闸门的真实代价

| 闸门 | 好处 | 代价 |
|---|---|---|
| 计划审批 | 方向可控；拒绝时磁盘零变化 | 多一次交互；计划可能过时 |
| 写操作确认 | 每步可控 | **7 个任务按 7 次 y，人会疲劳** |
| 事后复查 | 能发现错 | 发现时已经改了 |

**「确认疲劳」是真实问题**：按第 5 次 y 时人已经不看了。所以 V4 才要做内容预览（`describe_write_v4`）——**让每一次确认都有信息量**。

## 一个容易被忽略的设计点

V4 里有个前置检查（`tools_v4.py` 的 write_file 分支）：

```python
if target.exists() and not args.get("overwrite"):
    return f"工具执行失败：目标已存在，拒绝覆盖（需要 overwrite=true）"
```

**放在问 y 之前。**

为什么？如果放后面，用户会先看到「写入 report.md」按了 y，然后才收到「目标已存在，拒绝覆盖」——**白按一次，而且会以为是自己批准的错**。

> **原则**：**所有「注定失败」的检查，都要放在「请求人确认」之前。**

这条在任何有确认流程的系统里都成立。

# 9. 循环的实现形态（回答「agent 是不是都是 while 循环」）

## 本质是循环，但写法可以不同

| 形态 | 例子 | 本质 |
|---|---|---|
| `while True` + `break` | 多数手写 agent | 直接循环 |
| `for i in range(N)` | **本项目** | 直接循环 + 轮次保险 |
| 递归 | 函数调用自己 | 循环的等价写法 |
| 事件回调 | streaming / UI 驱动 | 循环被拆成回调链 |
| 图遍历 | LangGraph 的 `StateGraph` | 循环 = 图上的**环** |
| 框架隐藏 | LangChain `AgentExecutor` | 内部还是 while，只是你看不见 |

## 判定标准不是 `while` 关键字

**是这两件事**：

1. **路径长度不确定**：跑几步由运行时决定，不由代码写死
2. **分支由模型输出决定**：下一步做什么，看模型说了什么

满足这两条，即使你写成递归、写成事件机、写成图，它也是 agent。
不满足，即使你写了 `while`，它也不是 agent。

```python
# 这是 while，但不是 agent —— 路径和分支都是写死的
while i < 10:
    call_model(...)
    i += 1

# 这是递归，但它是 agent —— 分支由模型决定
def step(messages):
    data = call_model(messages)
    if data["stop_reason"] == "tool_use":
        return step(messages + [run_tools(data)])   # ← 递归即循环
    return data
```

## 为什么多数实现选 `for range(N)` 而不是 `while True`

| | `while True` | `for range(N)` |
|---|---|---|
| 意外情况下 | 可能无限循环 | 一定有上限 |
| 代码可读性 | 控制流不明确 | 上限一目了然 |
| 调试 | 不好定位第几轮 | `step` 变量就是轮次 |

**本项目的选择是对的**：`for step in range(MAX_ITERATIONS)`，`step` 还能用来打日志。

## 关于「成熟 agent 也都是 while 吗」

**单 agent 的：基本是。** 因为本质就是「模型输出决定下一步」。

**多 agent 的：不一定。** 常见形态：

| 形态 | 循环在哪 |
|---|---|
| **管理者-工人**（orchestrator-worker） | 管理者一个循环，每次派活给工人 |
| **群聊式**（AutoGen 的 group chat） | 由「轮到谁说话」的调度器驱动，不是单一 while |
| **流水线 + 局部循环** | 整体是 DAG，某些节点内部是 agent 循环 |

**但注意**：多 agent 在 90% 的场景里是过度设计。这一点面试可以主动说，会加分。

# 10. 对照成熟产品：三个具体设计

## ① Manus：复述 + 不清历史

- **复述**：让 agent 反复重写 `todo.md`，把目标推到上下文「近期」位置
- 道理：模型对**越靠后**的内容注意力越强
- **本项目的等价物**：`execution_prompt` 每轮重新 `plan.render()`

- **不清历史**：失败的工具调用留在上下文里
- 道理：模型看到「上次这么干失败了」才知道换方法
- **本项目的等价物**：`tool_result` 里的错误原文保留

## ② Claude Code：分节 + 动态注入 + 压缩

- system 分节：语气 / 主动性 / 遵循约定 / 任务管理 / 工具策略 / 代码引用格式
- 每轮动态注入：`CLAUDE.md`、git 状态、目录结构
- `/compact` 触发 L2 压缩记忆
- **本项目的差距**：我们只有 system 常量（V4）或 plan 注入（V5），没有项目约定文件，没有压缩

## ③ Cline：显式结束工具

- 用 `attempt_completion` 工具来**宣告完成**，而不是靠「模型不再调工具」推断
- **本项目的等价物**：`update_task(id, "done")` + `plan.is_complete`
- **这条比你想的重要**：靠「不再调工具」判断结束是很脆的——模型可能只是话说到一半被截断

> **原则**：**「完成」应该是显式的、可验证的信号，不是推断出来的。**

# 11. 你这个项目的架构评价

## 做对的五件事

| # | 做对了什么 | 为什么重要 |
|---|---|---|
| 1 | **两道闸门分层** | 粗粒度控方向、细粒度控动作 |
| 2 | **阶段隔离用工具清单** | 安全从「相信模型」变成「结构上不可能」 |
| 3 | **计划是对象不是文本** | 「完成」可计算、可存、可恢复 |
| 4 | **原子写存档** | 长任务里崩溃概率不低，半个 JSON 就全废 |
| 5 | **发现状态-历史不一致** | 这是很多商业产品也没处理好的问题 |

## 真实的四个洞

| # | 洞 | 后果 | 修法 |
|---|---|---|---|
| 1 | `messages` 只增不减 | 越用越贵，最终撞预算半路停 | 阶段 3 选项 A：裁剪 |
| 2 | 没有评测 | 改提示词只能肉眼看 | 阶段 4.2 |
| 3 | `in_progress` 状态模糊 | 恢复后不知道从哪继续 | 已有 `/retry` 兜底，但没有自动化 |
| 4 | 确认闸门阻塞 `input()` | 没法做成服务 | 阶段 4.1：改成异步确认状态 |

**第 4 条面试特别爱问**：「你这个能做成服务吗？」——直接答「不能，因为确认闸门是阻塞的 `input()`」，然后说「改法是把待确认动作存进会话状态，客户端再调 `/confirm`」。**承认缺陷 + 给出方案，比硬说能做更好。**

# 12. 面试追问链（10 连问）

这是最可能的深挖路径，每一问他都可能接着问下去。

> **Q1**：你的 agent 是怎么工作的？
> A：一个循环——把历史发给模型，看 `stop_reason`，如果要工具就执行并回填，再问。次数由模型决定，有轮次和预算两个保险。

> **Q2**：模型服务端不存对话，它怎么「记住」上一句？
> A：靠每轮全量重发 `messages`。所以「记忆」在本地，不在服务端。

> **Q3**：那长对话怎么办？
> A：（本项目）没处理，这是缺陷。（成熟做法）滑动窗口 / 摘要压缩 / 外部存储检索。

> **Q4**：怎么防止它删你文件？
> A：三层。①工具集里根本没有删除工具 ②所有路径过 `safe_path`（先 resolve 再 `is_relative_to`）③写操作要 y/N，默认拒绝。

> **Q5**：提示词里写了「只能操作 workspace」，这够吗？
> A：不够。提示词是建议，模型可以不遵守。真正拦它的是 `safe_path` 和 `registry`——`registry` 里没有的函数，它点不出任何后果。

> **Q6**：为什么要「计划审批」和「写操作确认」两道闸门？
> A：粒度不同。计划管方向（7 件事对不对），写操作管每一步（这一步要不要做）。合成一道就同时失去两个粒度。

> **Q7**：你怎么保证模型不改你批准的计划？
> A：改计划的 5 个命令只存在于 REPL，不在模型工具清单里。模型只能改任务状态（`update_task`），不能增删任务。

> **Q8**：中断了怎么恢复？
> A：现场六项落盘（goal/phase/plan/messages/budget），原子写。因为模型无状态，原样发回去就能接上。但要处理 `in_progress` 的歧义——所以有 `/retry`。

> **Q9**：模型为什么会「罢工」？
> A：因为历史里有条过期结论（「预算已用完，工具未执行」），它只能看见历史，看不见内存里的 budget。修法是**加一条新消息覆盖，而不是删旧消息**。

> **Q10**：改提示词后你怎么知道变好了？
> A：（本项目）不知道，这是缺陷。（方案）固定任务集 + 自动断言 + 通过率对比。

# 13. 一页速记

```
agent = 循环，次数和分支由模型运行时决定
     ↓
六个零件：初始状态 / 调用 / 判定 / 副作用 / 回填 / 终止
     ↓
三种终止：模型自己停 · 轮次上限 · 预算上限
     ↓
三种驱动：用户驱动（V1-V4）· 计划驱动（V5-V6）· 事件驱动
     ↓
三份状态：messages（模型看）· plan（render 后模型看）· budget（模型看不见）
     ↓
五组矛盾：能力/安全 · 自主/可控 · 状态/对话 · 便宜/完整 · 灵活/可测
     ↓
四层记忆：工作(messages) · 压缩(摘要) · 外部(文件/RAG) · 参数(权重)
     ↓
三道闸门：事前(计划) · 事中(写确认) · 事后(复查)
     ↓
一条铁律：内存改了状态，就必须产生一条消息，否则模型看不见
```
