# V5：显式计划、两道闸门、断点恢复

## 1. 这一版做了什么

V4 的「计划」是模型在回答里说的一段话——它可能说 6 步，也可能跳过勘察直接开干，代码里没有任何东西知道「现在做到第几步」。

V5 把计划变成**代码里的对象**：

| | V4 | V5 |
|---|---|---|
| 计划存在哪 | 提示词里的一段文字 | `Plan` 对象，带任务列表和状态 |
| 谁能改计划 | 模型随时可以改口 | 只有 `create_plan`，且只在规划阶段 |
| 做完了吗 | 模型说了算 | `plan.is_complete` 算出来 |
| 中途退出 | 只有聊天记录，得重来 | `sessions/*.json`，`/resume` 接着做 |
| 动手前 | 写操作 `y/N` | 写操作 `y/N` **+ 计划审批 `y/N`** |

四件事，从下往上：

1. **`Plan` / `Task` 状态机**（`agent/plan.py`，114 行）：5 种状态、最多 12 个任务，能渲染、能存 JSON。
2. **阶段隔离**（`agent/tools_v5.py`，98 行）：规划阶段**只给只读工具 + `create_plan`**，执行阶段给 6 个写工具 + `update_task`。不是靠提示词劝，是工具清单里压根没有。
3. **两道闸门**：计划批准了才动手；动手时每个写操作还要再按一次 `y`。
4. **断点恢复**（`agent/session_store.py`，53 行）：`goal / phase / plan / messages / budget` 原子写盘，`/resume` 读回来接着跑。

入口 `src/v5_planner.py`（433 行），V3 / V4 的入口一行没改。

### 2.2 `Plan`：把计划变成可检查的数据（`plan.py`）

状态只有五个，而且是**闭集**（`plan.py` 第 6–7 行）：

```python
STATUSES = ("pending", "in_progress", "done", "failed", "skipped")
MAX_TASKS = 12
```

拿到模型给的标题，先洗数据再建对象（第 32–49 行）：

```python
def set_tasks(self, titles: list[str]) -> None:
    if not isinstance(titles, list):
        raise ValueError("tasks 必须是字符串数组")
    clean = []
    for title in titles:
        if not isinstance(title, str):
            raise ValueError("每个任务都必须是字符串")
        title = title.strip()
        if title:
            clean.append(title)
    if not clean:
        raise ValueError("计划至少需要一个任务")
    if len(clean) > MAX_TASKS:
        raise ValueError(f"计划最多 {MAX_TASKS} 个任务，收到 {len(clean)} 个")

    self.tasks = [Task(id=i + 1, title=t) for i, t in enumerate(clean)]
    self.touch()
```

改状态也是**先校验再改**（第 51–63 行）：

```python
def update(self, task_id: int, status: str, note: str = "") -> Task:
    if status not in STATUSES:
        raise ValueError(f"未知状态：{status}，可用：{', '.join(STATUSES)}")
    task = next((t for t in self.tasks if t.id == task_id), None)
    if task is None:
        raise ValueError(f"没有编号为 {task_id} 的任务（共 {len(self.tasks)} 个）")

    task.status = status
    if note is not None:
        task.note = str(note).strip()[:200]
    self.touch()
    return task
```

为什么要这么较真？因为**这两个方法是模型能碰到的唯一入口**。模型可能传 `status: "finished"`、`task_id: 99`、20 个任务。这些输入不会被当成「大概意思对了」放过去，而是变成一句错误文字回喂给它——模型下一轮自己改（V1 就定下的原则：错误信息是给模型看的）。

「做完了吗」由代码算，不由模型说（第 65–71 行）：

```python
@property
def done_count(self) -> int:
    return sum(1 for t in self.tasks if t.status in ("done", "skipped"))

@property
def is_complete(self) -> bool:
    return bool(self.tasks) and all(t.status in ("done", "skipped") for t in self.tasks)
```

`failed` 不算完成。运行 B 里模型把任务 7 标成 `failed`，程序就报「还有 1 个任务未完成」——这不是程序不听话，是定义如此。

`render()`（第 76–84 行）只干一件事：把对象拍成给人看的文本。计划在终端打印、塞进 system prompt、随工具结果回显，用的都是同一个 `render()`，所以三处永远一致。

Java 类比：`Task` / `Plan` 就是两个 POJO，`STATUSES` 是 enum，`set_tasks` / `update` 是带参数校验的 setter，`is_complete` 是 `boolean isComplete()` 计算属性。整个 `plan.py` 没有任何 I/O，纯数据。

### 2.3 阶段隔离：靠工具清单，不靠提示词（`tools_v5.py`）

```python
READ_ONLY_NAMES = {"list_dir", "read_file", "search_files"}
READ_TOOLS = [t for t in TOOLS_V4 if t["name"] in READ_ONLY_NAMES]
EXECUTION_NAMES = [t["name"] for t in TOOLS_V4]

PLANNING_TOOLS = READ_TOOLS + [CREATE_PLAN_TOOL]
EXECUTION_TOOLS = TOOLS_V4 + [UPDATE_TASK_TOOL]
```

（第 6–8、43–44 行）

两套清单，发给模型的 `tools` 字段就是这两套之一。**规划阶段的 HTTP 请求里根本没有 `write_file` 这个工具**，模型想调也调不出来。

但「清单里没有」还不够——模型可能自己编一个工具名。所以分发函数还有第二道检查（第 47–79 行）：

```python
def run_planning_tool(name: str, args: dict, plan: Plan, log=None) -> tuple[str, bool]:
    if name == "create_plan":
        ...
    if name in READ_ONLY_NAMES:
        return run_v4_tool(name, args, log=log), False
    return (
        f"规划阶段不能调用 {name}。可用：create_plan, "
        + ", ".join(sorted(READ_ONLY_NAMES))
    ), False
```

不调模型直接测的结果：

```
规划阶段 write_file -> 规划阶段不能调用 write_file。可用：create_plan, list_dir, read_file, search_files | created = False
执行阶段 create_plan -> 执行阶段不能调用 create_plan。可用：update_task, list_dir, read_file, mkdir, move_file, search_files, write_file
执行阶段 update_task -> 任务 1 → done：a
非法状态 -> 工具执行失败：未知状态：finished，可用：pending,
```

两个方向都堵上了。这是 V3 沙箱思路的延续：**权限边界写在代码里，不写在提示词里**。

### 2.4 闸门一：计划审批（`v5_planner.py` 第 168–175 行）

```python
def approve_plan(plan: Plan, ask=None) -> bool:
    print("\n" + plan.render())
    ask = ask or input
    try:
        answer = ask("批准这个计划? (y/N) ")
    except EOFError:
        answer = ""
    return answer.strip().lower() == "y"
```

只有 `y` 算批准，回车、`Y`（被 lower 掉）、其他任何输入都算拒绝。拒绝后走的是这段（第 401–406 行附近）：

```python
logger.log("plan_rejected", tasks=len(plan.tasks))
print("（计划未批准，已放弃；磁盘没有发生任何变化）")
save_session(store, goal, "rejected", None, [], budget, logger.log)
plan = None
messages = []
phase = "idle"

```

注意它把计划**丢掉**了（`plan = None`），不是留着等你改。V5 的取舍是「要么批准整份，要么重来」——「改第 3 条、删第 5 条」这种编辑功能留到以后。简单，但边界清楚。

### 2.5 闸门二：写操作确认，一个字都没改（`tools_v4.py` 第 128–148 行）

```python
if name in WRITE_TOOLS:

        if target.exists() and not args.get("overwrite"):
            return f"工具执行失败：目标已存在，拒绝覆盖（需要 overwrite=true）：{args.get('path')}"

    approved = answer.strip().lower() == "y"
    if not approved:

```

V5 只是把这套东西原样接过来（`run_execution_tool` 里 `return run_v4_tool(name, args, ask=ask, log=log)`）。

**两道闸门为什么要分开？** 因为它们是两种不同的问题：

- 计划审批回答的是「**这件事要不要做**」——整理 6 个文件、生成报告，你同意吗？
- 写操作确认回答的是「**这一步现在能不能落盘**」——这条 `move_file` 真的执行吗？

如果只有第二道，模型可以一边执行一边改主意，你会在第 5 个 `y` 时才发现它跑偏了。如果只有第一道，批准一份 7 步计划就等于授权 20 次磁盘写入。V5 两道都要。

### 2.6 存档：先写临时文件再替换（`session_store.py` 第 24–41 行）

```python
def save(self, *, goal: str, phase: str, plan, messages: list, budget) -> None:
    self.dir.mkdir(parents=True, exist_ok=True)
    payload = {
        "session_id": self.session_id,
        "goal": goal,
        "phase": phase,
        "plan": plan.to_dict() if plan is not None else None,
        "messages": messages,
        "budget": budget.to_dict(),
        "updated_at": datetime.now().isoformat(timespec="seconds"),
    }
    # 先写临时文件再替换：中途崩了也不会留下半个 JSON。
    tmp = self.path.with_name(self.path.name + ".tmp")
    tmp.write_text(
        json.dumps(payload, ensure_ascii=False, indent=2, default=str),
        encoding="utf-8",
    )
    tmp.replace(self.path)
```

`tmp.replace()` 在同一分区上是原子操作。如果直接 `path.write_text()`，写到一半断电就是**半个 JSON**——下次 `/resume` 解析失败，整个会话作废。这种「写到一半」的坑，写文件的人都踩过。

`latest()` 按 `mtime` 排序取最后一个（第 44–50 行），`load()` 就是 `json.loads`。

这三次运行留下的存档就是证据：

```
sessions\session-20261111-114423.json | phase= done | budget= {'max_tokens': 80000, 'input_tokens': 59212, 'output_tokens': 4375} | msg= 44
```

`sessions/` 已经在 `.gitignore` 里——里面是完整对话内容，不该进仓库。

### 2.7 恢复：搬的是状态，不是记忆（`v5_planner.py` 第 265–305 行）

```python
def load_resume(budget: Budget, store: SessionStore, log):
    path = SessionStore.latest()
    if path is None:
        print("（没有找到可恢复的会话存档）")
        return None
    ...
    plan = Plan.from_dict(data["plan"]) if data.get("plan") else None
    messages = data.get("messages") or []
    goal = data.get("goal") or (plan.goal if plan else "")
    phase = data.get("phase") or "idle"
    budget.restore(data.get("budget"))
    store.adopt(path)
    ...
    if phase == "done" or plan.is_complete:
        print("（这个计划已经完成，不需要继续）")
        return None

    return goal, phase, plan, messages
```

`store.adopt(path)` 很关键：恢复后继续保存时**写回同一个文件**，而不是新建一个。否则你恢复 3 次就多出 3 个半成品存档。

**恢复的是现场，不是模型的记忆。** 模型的「记忆」在 V2 就说清了：就是那串 `messages`。所以只要 `messages` + `plan` + `phase` + `budget` 都在，新进程接着发请求，模型看到的历史和退出前是同一份。

`budget.restore()` 是这一版唯一改 V4 文件的地方（`budget.py` 第 61–72 行）：

```python
def restore(self, data: dict | None) -> None:
    """从存档恢复用量。

    用量一定照搬（否则恢复等于偷额度）；上限取「存档值」和「本次环境变量值」
    中较大的那个——允许你把 MAX_SESSION_TOKENS 调大继续跑，但不允许悄悄调小。
    """
    data = data or {}
    stored_max = int(data.get("max_tokens") or 0)
    self.max_tokens = max(stored_max, self.max_tokens)
    self.input_tokens = int(data.get("input_tokens") or 0)
    self.output_tokens = int(data.get("output_tokens") or 0)
    self._warned = self.used >= self.max_tokens * WARN_RATIO
```

第一版写的是「上限也照搬存档值」，结果运行 A 那种「40000 用完了」的会话，`/resume` 之后**永远起不来**——一进循环就是 `used >= max_tokens`，你调环境变量也没用。改成 `max(存档, 本次)`：用量照旧（不能靠重启偷额度），上限允许你主动抬高（不能悄悄降低）。

### 2.8 入口的三个状态（`v5_planner.py` 第 336–418 行）

REPL 里其实只有三种输入：

```python
if line == "/clear":
    messages = []; plan = None; goal = ""; phase = "idle"; resume_ready = False
    budget.reset(); store = SessionStore()
    ...
if line == "/plan":
    print(plan.render() if plan is not None else "（当前没有计划）")
    continue
if line == "/resume":
    loaded = load_resume(budget, store, logger.log)
    if loaded:
        goal, phase, plan, messages = loaded
        resume_ready = True
        print("输入「继续」接着执行；输入其他内容会作为新任务重新规划。")
    continue

# 恢复后输入「继续」：不再重新规划，直接接着执行。
if line == "继续" and resume_ready and plan is not None:
    ...
    phase = execution_phase(goal, plan, messages, budget, store, logger.log)
    continue

# 新任务：清空上一轮的对话，重新规划。
goal = line
messages = []
plan = None
phase = "planning"
```

（为了看清分支，这里把中间几行省略了，`/resume` 之后对 `awaiting_approval` 的二次审批在第 361–375 行。）

`/resume` 之后**故意不自动继续**：恢复完只打印现场，等你打「继续」。因为恢复一个 6/7 的计划，下一步就是 10k token 的模型调用——不该因为你手滑打了个 `/resume` 就自动烧钱。

`/clear` 只清内存并新建一个 `SessionStore`，**不删旧存档**。想回去还能 `/resume`。

## 3. 值得记住的三件事

### ① 计划成为一等公民

V4 的「计划」在提示词里，模型下一次回答就可能不认账；V5 的计划是 `Plan` 对象，有编号、有状态、能被 `is_complete` 检查、能被 `to_dict` 存盘。

区别在可验证性：V4 你只能读它的文字，判断「它是不是真按说的做了」；V5 你问 `plan.tasks`，`pending` 就是没做。

但代价也真实：**计划一旦固定，模型就不能在执行中发现「其实该先删旧文件」并自行改计划**。V5 故意的——先跑通「说到做到」，再谈「边做边改」。

### ② 两道闸门，管的是两种不同的决定

批计划 = 同意目标和方法；批写操作 = 同意这一次落盘。合并成一道，就等于「批了一份 7 步计划，后面 20 次写入全自动」。

反过来，只有写操作确认也不行：你会在第 5 个 `y` 时才发现它把「其他文件」理解成了「除 .jpg/.txt 外全部」，包括你想留着的 `.zip`。

顺带一个观察：运行 A 里模型主动决定**不移动 `.gitkeep`**（0 字节的 git 占位文件），还写进报告说明了理由。两道闸门的意义就在这儿——它有权提议例外，但报告要给你看，你也可以在第 7 个 `y` 时否决。

### ③ 断点恢复靠「状态」，不靠「记忆」

模型没有记忆，`messages` 就是全部记忆。所以「接着做」= 把 `messages` + 计划 + 阶段 + 预算 原样塞回去。

这也解释了一个反直觉现象：运行 B 里 `/resume` 成功了，但结果不理想——因为**历史里躺着一条「预算已用完」的 `tool_result`**，模型据此判断「这活干不成了」。恢复搬过来的是现场，包括现场里的坏消息。

想让它重试，得给它新的信息（比如「预算已加到 80000，请重跑任务 7」）。这是下一版可以做的「人工接管」。

## 4. 踩过的坑（都是实测）

### 坑 1：默认 20000 预算对 V5 偏紧

V5 要跑两遍（规划一遍、执行一遍），每次请求都要重发全部历史。实测一次完整 7 任务流程用了 **63587 tokens**。

| 阶段 | 说明 |
|---|---|
| 规划 | 只读勘察 + `create_plan`，几轮就结束 |
| 执行 | 每轮带完整 `messages`，越到后面 input 越大 |

所以跑 V5 建议 `$env:MAX_SESSION_TOKENS = "80000"`。默认值当时没改，是因为它是「保险丝」不是「配额」——不知道要花多少时，小一点更安全。

> 补充（V6 时）：`DEFAULT_MAX_TOKENS` 后来被调到 `100000`。这是个可以随便调的旋钮——**上面这个坑讲的不是「数字应该多大」，而是「检查点太稀，数字多大都可能被单轮冲爆」**。

### 坑 2：预算只在每轮开头检查，单轮能冲出去

运行 A 最后一行：`49088/40000`。不是算错，是**检查点太稀**：这一轮模型一次性要了 7 个工具调用，其中 `write_file` 正文 1093 字符，一轮就 1 万多 token。检查发生在调用前，调用后才发现超了。

更规范的做法是「发请求前预估本轮成本」或「按工具逐个检查预算」。V5 没做，只保证**超了就不再调模型、不执行剩余工具**，并把没执行的调用补一条 `tool_result`，让历史保持合法（第 61–82 行）——否则 Anthropic 接口会因为「有 `tool_use` 没有对应 `tool_result`」直接报错。

### 坑 3：16 轮循环上限，装不下 7 个任务

`EXECUTION_MAX_ITERATIONS = 16`。实测跑到 6/7 就转满了：

```
（这一轮转满了 16 次工具循环，计划可能还没做完）
```

原因是每个任务至少两轮（`update_task in_progress` + 干活），7 个任务 + 补充复查轻松超过 16。输入「继续」后，3 个工具调用就收尾了。

这两个上限（预算、轮次）都是保险丝：**会误伤，但不会丢状态**。状态每轮都存盘，断了就 `/resume` 或者打「继续」。

### 坑 4：模型会中途停下来说话

第一次跑到第 5 个任务时，模型输出了一段「现在生成 report.md」的文字，**但没有调工具**，循环把控制权交回了用户。修法是在执行提示词里加一条：

```
4) 只要计划里还有 pending / in_progress 的任务，就继续调用工具推进，不要停在半路等用户说话；
```

这不是「让模型更聪明」，是把「循环什么时候停」这件事说清楚。V5 的循环本身只认 `stop_reason`：`tool_use` 就继续转，别的就停。

### 坑 5：`failed` 让计划永远「未完成」

运行 B 里，模型因为预算历史把任务 7 标成 `failed`，然后 `is_complete` 返回 `False`，程序提示「还有 1 个任务未完成」，模型自己也说「6/7 完成，1 项 failed」。

这三个东西是一致的，不是矛盾：`failed` 是「试过但没成」，`skipped` 是「不用做」。想让计划收口，要么把任务重新做成 `done`，要么明确 `skipped`。V5 没提供「重置任务状态」的工具——模型可以把 `failed` 再改成 `done`，但得先真的做成。

## 7. V5 没做的事（留给以后）

- **不能改计划**：批准后模型只能执行，不能删任务、加任务、调顺序。
- **不能人工接管**：恢复后只能「继续」或「当新任务重来」，没法说「跳过任务 7，直接做任务 8」。
- **单会话单计划**：REPL 里只有一个 `plan`，新输入会覆盖旧计划（提示一句，但旧计划不保留）。
- **不能并行**：工具调用是串行执行的，哪怕模型一次给了 7 个。
- **没有跨会话检索**：`/resume` 只找最近一个存档，`sessions/` 里的历史存档没有列表命令。

这些不是遗漏，是**下一版才有资格做的东西**：先证明「计划能被完整执行」，再谈「计划能被灵活修改」。
