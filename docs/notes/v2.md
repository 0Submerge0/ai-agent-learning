# V2：多轮对话与记忆

## 1. 这一版做了什么

把 V1 的「问一句答一句」改成**同一个进程里能连续聊**：它记得你说过什么，还多了两个命令——`/clear`（手动失忆）和 `/exit`（退出）。

```powershell
uv run python src/v2_repl.py
```

进去之后它会变成交互式，`你>` 是输入提示符。真实输出（连聊了 5 轮）：

```
V2 交互式助手。输入 /clear 清空记忆，/exit 退出。
你> 助手> 好的，阿杰，记住了。👌

有需要我帮忙看文件或目录，随时说。

[用量] 本次输入 77 / 输出 223 tokens
你> 助手> 你叫阿杰。😊

有需要查看的文件或目录，随时告诉我。

[用量] 本次输入 307 / 输出 19 tokens
你> （记忆已清空）
你> [工具] list_dir({"path": "."})
       .env.example  301 B
       ...
[工具] list_dir({"path": "docs/notes"})
       v0.md  12395 B
       v1.md  10933 B
助手> 抱歉，我不知道你的名字——我们这次对话没有包含任何关于你身份的信息，
我这边也没有保存过你的个人资料。我查看了当前工作目录……里面只有项目代码和
笔记（docs/notes/v0.md、v1.md），没有找到任何写着用户名字的文件。

[用量] 本次输入 192 / 输出 190 tokens
你> （/exit）
```

看懂这五行输出，V2 就学完一半了：

1. 第一轮：我说「记住我叫阿杰」→ 它说记住了。
2. 第二轮：我问「我叫什么名字」→ 它答「阿杰」。**这就是记忆。**
3. `[用量] 本次输入` 从 **77 → 307**：多出来的 ~230 个 token 就是「把上一轮的历史也重发了一遍」花掉的。记忆是有成本的，而且这个成本你每轮都能看见。
4. `/clear` 之后：再问「我叫什么名字」→ 它**答不上来**。而且它自己调用工具去项目文件里找有没有写着名字的文件——因为它知道上下文里已经没有任何关于你的信息了。
5. 最后一行是 V1 的伏笔：失忆后它仍然会调工具。**工具能力和记忆是两回事。**

## 2. 代码逐块讲

V1 的东西几乎全部保留（`TOOLS`、`list_dir`、`run_tool`、`extract_text` 一行没改）。新增/改动的是下面几块。

### 2.1 开头多了三行（第 14–16 行）

```python
# input() 从 stdin 读：管道/IDE 传进来的中文可能被按 GBK 解读，这里也统一成 UTF-8。
if hasattr(sys.stdin, "reconfigure"):
    sys.stdin.reconfigure(encoding="utf-8", errors="replace")
```

V2 引入了 `input()`（交互式读一行），而 Windows 的管道/IDE 默认把中文按 GBK 解读，`input()` 读进来就是乱码。实测过：不修这行，「记住我叫阿杰」发过去模型看到的是「璁颁綇鎴戝彨闃挎澃」，它还自己发现了「这像是 UTF-8 被按 GBK 解读了」。加上这行才恢复正常。

**为什么是 `if hasattr(...)`**：Linux/macOS 的 stdin 本来就是 UTF-8，`reconfigure` 方法不存在或没必要——这个守卫让同一份代码在三个平台都能跑。

### 2.2 `ModelError` 类（第 70–71 行）

```python
class ModelError(Exception):
    """模型调用失败。REPL 会捕获它并继续聊天，不让程序死掉。"""
```

**Java 类比：这就是一个自定义的 `RuntimeException` 子类。** V1 里调用失败是 `sys.exit(1)`——程序当场死掉；V2 改成 `raise ModelError(...)`——把失败变成异常**抛出去**，由上层（REPL）决定怎么处理。这是「进程不死」的基础。

### 2.3 `call_model`：失败不退出 + 自动重试（第 74–123 行）

变化一：**所有 `sys.exit` 都换成了 `raise ModelError`**。第 78 行（没 key）、第 107 行（网络失败）、第 110 行（请求没发出去）、第 115 行（HTTP 非 200）、第 121 行（返回不是 JSON），全都只抛异常、不退出进程。

变化二：**网络抖动自动重试**（第 89–107 行）：

```python
for attempt in range(retries + 1):
    try:
        resp = requests.post(...)
    except (requests.exceptions.Timeout, requests.exceptions.ConnectionError) as exc:
        # 网络抖动：自动重试，而不是立刻放弃。这是「错误重试」的第一版。
        if attempt < retries:
            print(f"（网络抖动，重试第 {attempt + 1} 次）", file=sys.stderr)
            continue
        raise ModelError(f"网络请求失败：{exc}")
```

- `retries` 是函数参数，默认 `2`（第 74 行签名 `retries: int = 2`），调用方可以传 0 关掉重试。
- `range(retries + 1)` 一共允许 `retries + 1` 次尝试（第 1 次 + 2 次重试）。
- 只有**网络类异常**（超时、连不上）才重试；HTTP 400/401 这类服务端明确拒绝的**不重试**——重试也没用，只会多花钱。这个区分值得记住：**可重试的是「暂时性故障」，不可重试的是「确定的拒绝」。**

变化三：**HTTP 错误响应体会截断**（第 115 行）`resp.text[:300]`——只留前 300 个字符，避免服务端一大段错误文本刷屏。

### 2.4 `run_turn`：一次提问的内部循环（第 132–171 行）

从 V1 的 `run_agent` 改来。V1 的 `run_agent(question)` 自己在内部造 `messages`，只服务一次提问；V2 把 `messages` 的所有权交了出去：

```python
def run_turn(messages: list) -> list:
```

- **`messages` 由 REPL 传进来，处理完再返回**。内部仍然是 V1 那套循环：`call_model` → 原样回填 assistant → 如果是 `tool_use` 就执行工具、结果塞回 → 继续；不是就打印答案返回（第 137–168 行）。
- 末尾多了上下文预警（第 166–167 行）：`messages` 超过 20 条就提示「历史很长，费用在涨，可以 /clear」——让「上下文膨胀」这件事可见。

**一个 Python 细节，Java 开发者会心一笑**：`messages` 是 list，传进函数后 `messages.append(...)` 改的是**同一个列表**（Java 的 `List` 也一样，引用传递）。所以 `run_turn` 内部其实已经在原地改历史了，`return messages` 只是「明说我要还你一个更新的历史」——代码读起来更清晰，也留给将来「内部重建列表」的余地。

### 2.5 `run_repl`：交互式主循环（第 174–198 行）

V2 真正的新东西。整段就一个 `while True`：

```python
def run_repl() -> None:
    messages = []  # 这是「记忆」本体：全程存活，每轮全量重发
    print("V2 交互式助手。输入 /clear 清空记忆，/exit 退出。")
    while True:
        try:
            line = input("你> ")
        except (EOFError, KeyboardInterrupt):  # Ctrl+D / Ctrl+C
            break
        line = line.strip()
        if not line:
            continue
        if line == "/exit":
            break
        if line == "/clear":
            messages = []
            print("（记忆已清空）")
            continue

        messages.append({"role": "user", "content": line})
        try:
            messages = run_turn(messages)
        except ModelError as exc:
            print(f"调用失败：{exc}")
            print("（可以再试一次，或者输入 /clear 重来）")
```

逐行翻译：

- **第 175 行 `messages = []`——这是 V2 的灵魂。** 它在 REPL 启动时创建、全程存活。对比 V1：V1 的 `messages` 在 `run_agent` 里创建、函数一返回就没了。V2 只是把这个列表「活得久一点」。
- **第 179 行 `input("你> ")`**：Java 的 `System.console().readLine()` / `Scanner.nextLine()`，读一行用户输入。
- **第 180–181 行**：`Ctrl+D`（EOFError，Windows 上输入流结束）或 `Ctrl+C`（KeyboardInterrupt）时 `break`，静默退出，不打印 traceback。
- **第 182–184 行**：空行直接跳过（`strip()` 去首尾空白）。
- **第 185–186 行 `/exit`**：`break` 退出循环。
- **第 187–190 行 `/clear`**：`messages = []`——**失忆的全部实现就是这一行**。它把历史整个扔掉。
- **第 192 行**：普通输入 → 把这条 user 消息 `append` 进历史。
- **第 193–197 行**：`run_turn` 抛 `ModelError` 时**捕获、打印、回到 `你>`**。这就是「网络挂了 REPL 不死」的实现。

## 3. 值得记住的三件事

### ① 记忆 = 你的 `messages` 列表，不是模型的能力

**模型那边永远没有记忆。** 它每一次收到请求，看到的都只是你这次发过去的 `messages` 数组——里面是什么它就看到什么，里面没有你叫阿杰，它就答不上来。

「它记得你」这个感觉，是**你在每次请求里把全部历史全量重发**制造出来的假象。证据就是那行用量数字：第二轮 `[用量] 本次输入 307`，比第一轮的 77 多了 230 个 token——那就是历史被重发一次的成本。

**Java 类比：这就像无状态 HTTP。** 服务器不记得你是谁，是客户端每次请求都带上 session cookie，才让服务器「看起来记得」。你的 `messages` 就是那个 cookie，只是它越来越大。

推论（V3+ 会遇到）：历史越长，每轮请求越贵、越慢。所以真实 agent 都有「压缩历史」或「只留最近 N 轮」的手段。V2 先给你看成本长什么样。

### ② `/clear` 是手动失忆，而且失得干干净净

它的实现只有一行：`messages = []`。清空后再问「我叫什么名字」，它立刻答不上来——甚至自己去翻项目文件找你的名字。这反过来证明了第 ① 点：**清空历史 = 清空它的记忆，因为记忆本来就在历史里。**

注意一个细节：`/clear` 连**工具结果也一起清了**。上面真实输出里，失忆后它不得不重新调 `list_dir` 去看目录——因为它「刚才看过目录」这件事也在历史里，被一起清掉了。

### ③ 工具结果留在历史里，下一轮还能引用

V2 里 agent 的记忆不只是「对话」，还包括「它做过的事」。实测：

```
你> 看看当前目录里有什么文件
（它调 list_dir，结果进了历史）
你> 刚才看到的目录里有没有 src 这个文件夹
助手> 有的，当前目录中存在 src 文件夹。在上面的列表中它位于目录部分，
      src  <dir> 表示它是一个子目录。
```

它记得「上一轮看过目录」——因为 `run_turn` 把 `tool_result` 也 `append` 进了 `messages`（第 156 行），历史里既有对话又有工具结果。**这正是 agent 和聊天机器人最早的分叉点**：聊天的历史只有「话」，agent 的历史还有「做过的事」。

## 4. 改一改试试（三条都实测过）

**1. 观察：连续问，看用量数字涨。**

进去后问「记住我叫阿杰」，再问「我叫什么名字」，对比两次的 `[用量] 本次输入`：

```
[用量] 本次输入 77   ← 第一轮：只有你这一句
[用量] 本次输入 307  ← 第二轮：历史全量重发
```

这 ~230 token 的差值就是「记忆的代价」。再问几轮，数字还会继续涨——直到超过 20 条消息，你会看到那句提示「历史已经很长，上下文费用在涨，随时可以输入 /clear」。

**2. 把第 15 行注释掉（`sys.stdin.reconfigure`），再跑记忆演示。**

实测（没修这行时的输出）：

```
你> 助手> 你好，阿杰！我记住你叫阿杰了。
（顺便提一句：你发来的那句话在我这边显示成了乱码「璁颁綇鎴戝彨闃挎澃」，
看起来像是 UTF-8 编码的文字被按 GBK 解读了，原始内容应该是「记住我叫阿杰」…）
```

模型**自己发现了编码问题**——因为管道传进去的中文在 Python 里就已经是乱码，模型收到什么就说什么。这是「stdin 要统一 UTF-8」这行存在的全部理由。

**3. 模拟断网：把 `API_URL` 指到一个不存在的地址，REPL 不崩。**

```python
import sys; sys.path.insert(0,'src')
import v2_repl as t
t.API_URL = 'https://ark.cn-beijing.volces.com/api/coding/v1/nope'
t.run_repl()
```

实测输出（我故意指错了路径，服务端返回 401）：

```
你> 调用失败：请求失败：HTTP 401 {...AuthenticationError...}
（可以再试一次，或者输入 /clear 重来）
你>
```

**进程没有死**——打印完错误就回到 `你>` 提示符，还能继续聊。这是 `ModelError` + REPL 捕获的效果：V1 里这种失败会 `sys.exit(1)` 直接退出，V2 变成「说一句、继续活」。真实场景里网络抖动很常见，这一版把「程序遇到失败」从「死掉」改成了「被接住」。

**Q2. `/clear` 做了什么？为什么清空后它立刻失忆？**

<details>
