# V6：计划可修改、人工接管

## 1. 这一版做了什么

V5 把计划变成对象，但批准之后就**锁死**了。实测撞到三个具体的死结：

| V5 的死结 | 现场 |
|---|---|
| 模型把任务标成 `failed` | 你只能看着，计划永远「未收口」 |
| 预算/轮次把执行拦腰截断 | 只能手打「继续」，打完还是原样重来 |
| 模型中途停下说话 | 没有「再推它一把」的正规手段 |

V6 把计划交还给人。新增 5 个命令 + 1 个「继续」，全部只改内存里的 `Plan`，改完立刻落盘：

| 命令 | 作用 |
|---|---|
| `/skip N` | 跳过任务 N（已 done 的会拒绝：跳过没有意义） |
| `/retry N` | 打回 `pending`，清掉上次的失败备注 |
| `/edit N 新标题` | 改任务描述，状态不动 |
| `/add 标题` | 末尾追加一个任务（上限 12） |
| `/rm N` | 删除并把后面的任务重新编号 |
| `/go` | 按当前计划继续执行 |

同时修掉 V5 §4 的三个坑：

1. **轮次按剩余任务缩放**：`max(16, 3 × 剩余任务 + 4)`，7 个任务给 25 轮，不再是固定 16。
2. **预算软着陆**：剩余预算不够下一轮时提前收尾，而不是等它冲爆。
3. **收口给分项统计**：`5 done / 1 skipped`，`failed` 时直接提示 `/retry` 或 `/skip`。

新入口 `src/v6_control.py`（约 270 行），**复用 `v5_planner` 的规划/审批/执行**，只加命令层。V5 入口一行没改。

## 2. 代码逐块讲

### 2.1 五个方法，都在 `Plan` 上（`plan.py` 第 86–162 行）

先有一个统一的查找，错误信息带总数：

```python
def find(self, task_id: int) -> Task:
    task = next((t for t in self.tasks if t.id == task_id), None)
    if task is None:
        raise ValueError(f"没有编号为 {task_id} 的任务（共 {len(self.tasks)} 个）")
    return task
```

跳过和重试（第 106–123 行）：

```python
def skip(self, task_id: int) -> Task:
    task = self.find(task_id)
    if task.status == "done":
        raise ValueError(f"任务 {task_id} 已完成，跳过没有意义")
    task.status = "skipped"
    if not task.note:
        task.note = "人工跳过"
    self.touch()
    return task

def retry(self, task_id: int) -> Task:
    task = self.find(task_id)
    task.status = "pending"
    task.note = ""
    self.touch()
    return task
```

`retry` 顺手清掉 `note`：那条备注写的是「上次为什么失败」，任务重做了还留着会误导模型。

删除要重新编号（第 146–162 行）：

```python
def remove(self, task_id: int) -> Task:
    """删除任务并重新编号 1..N。

    编号会变，因为人读的是序号（「第 3 个」），留着空洞只会让人困惑。
    历史对话里模型可能还在说旧编号，这是这个取舍的代价。
    """
    task = self.find(task_id)
    self.tasks.remove(task)
    for i, t in enumerate(self.tasks, start=1):
        t.id = i
    self.touch()
    return task
```

`counts()` / `summary()` 是给收口用的（第 93–103 行）：`{"done":5,"skipped":1,...}` → `"5 done / 1 skipped"`。

### 2.2 为什么模型不能改计划

V5 的执行阶段给了 `update_task`，它只能改**状态**。V6 没给模型加任何新工具——`/skip`、`/add` 这些命令只在 REPL 里，模型看不见也调不到。

这是 deliberate：**计划是用户批准的，改动权就该在用户手上**。如果模型能自己 `add_task`，那「你批准的是这 7 步」这句话就不成立了——它随时可以变成 8 步，而你只在事后才看见。

代价是模型发现「其实还该删个旧文件」时只能嘴上说，不能自己加一步。这个代价 V6 认了：先保证「计划是人说了算」，再谈「模型有建议权」。后者需要「提议 → 审批」的新流程，留给下一版。

### 2.3 执行阶段的三个修复（`v5_planner.py` 第 178–291 行）

两个**可选**参数，不传时 V5 行为一字不变：

```python
def execution_phase(
    ...,
    ask=None,
    max_iterations: int | None = None,
    soft_landing: bool = False,
) -> str:
    limit = max_iterations or EXECUTION_MAX_ITERATIONS
    last_cost = 0
```

**轮次缩放**在调用方算（`v6_control.py` 第 38–43 行）：

```python
def iterations_for(plan: Plan) -> int:
    """轮次上限跟着剩余任务走：每个任务至少两轮（标 in_progress + 干活）。

    V5 固定 16 轮，7 个任务实测会转满；这里给足，下界仍是 16。
    """
    return max(16, 3 * remaining_tasks(plan) + 4)
```

实测：剩余 3 个任务 → 16，7 个 → 25，12 个 → 40。下界仍是 16，因为短任务不该被削到 5 轮。

**软着陆**在循环开头（第 204–211 行）：

```python
# 软着陆：下一轮大概还是要花这么多，不够就现在收，别把任务拦腰截断。
if soft_landing and last_cost and budget.remaining < last_cost:
    print(
        f"（剩余预算 {budget.remaining} 不够下一轮（约 {last_cost}），提前收尾；"
        "进度已保存，可以 /go 接着做）"
    )
    log("soft_landing", phase="executing", remaining=budget.remaining, last_cost=last_cost)
    save_session(store, goal, "executing", plan, messages, budget, log)
    return "executing"
```

`last_cost` 是上一轮实际花的 token（`input + output`）。这个估算很粗——下一轮可能更贵——但比「等它冲爆」好：V5 实测有一次一轮吃掉 1 万多 token，直接把 40000 的预算干到 49088。

**收口分项**（第 267–277 行）：`soft_landing` 为真时打 `5 done / 1 skipped`，有 `failed` 就提示 `/retry` / `/skip`。V5 路径仍打原来的「还有 N 个任务未完成」——因为那是 V5 讲义里贴过的输出，不能悄悄改。

### 2.4 接管消息：光改状态不够（`v6_control.py` 第 91–135 行）

这是这一版最有意思的一段。第一次跑演示时，`/retry 4`、`/skip 6` 都成功了，`/go` 之后模型却连写三篇「我干不了」：

```
你> /go
（继续执行：剩余 2 个任务，本轮上限 16 次循环）
助手> ## 执行中断说明

我未能继续完成任务 4 和 5：调用 `move_file`（备份.zip → other/备份.zip）时返回 **"会话预算已用完，工具未执行"**，意味着该写操作根本没有发生，我没有反复重试。
...
[用量] 本次输入 1443 / 输出 641 tokens；会话累计 45084/100000 tokens（剩 54916）
```

连着三次 `/go`，一个工具都没调，白花了 800 多 token。

原因在历史的最后一条：恢复出来的 `messages` 里躺着一个 `tool_result`，内容就是「会话预算已用完，工具未执行」。**这条事实是真的发生过，但它现在过期了**。模型读到它，判断「工具不可用」，于是只肯写报告。

计划状态改了、预算也确实还剩 57000，但模型不知道——它只认历史。

修法是 `/go` 时补一条新的 user 消息，把情况说清楚：

```python
def takeover_message(plan: Plan, budget: Budget, edits: list[str]) -> str:
    parts = ["（人工接管）请继续执行计划，不要重复已完成的任务。"]
    if edits:
        parts.append("刚才人工做的调整：" + "；".join(edits) + "。")
    parts.append(
        f"当前进度：{plan.progress_text()}；剩余预算 {budget.remaining} tokens，"
        "工具可以正常调用（之前那条「预算已用完」是旧的，已经过期）。"
    )
    parts.append("当前计划：\n" + plan.render())
    parts.append("只处理状态为 pending / in_progress 的任务；done / skipped 的不要重做。")
    return "\n".join(parts)
```

`/go` 里发出去之前先追加：

```python
if messages:
    note = takeover_message(plan, budget, edits or [])
    messages.append({"role": "user", "content": note})
    log("takeover", edits=edits or [], chars=len(note), remaining=budget.remaining)
```

改完之后同一个 `/go`，模型第一件事就是 `update_task(4, in_progress)`。

为什么是 user 消息而不是改 system prompt？因为 system prompt 每轮都重发，写进它会变成永久指令（「你总是被人工接管」）；而这件事只在这一次接管时成立。用 user 消息 = 一次性的新事实，符合对话语义。

代价：每 `/go` 一次就多一条消息，历史变长。所以 `edits` 用完即清，消息里只带必要的现状。

### 2.5 命令层：解析与错误（`v6_control.py` 第 46–88 行）

```python
def apply_plan_command(line: str, plan: Plan) -> tuple[bool, bool, str]:
    """处理改计划的命令。返回 (是不是这类命令, 有没有改动, 给用户看的话)。"""
    parts = line.split(maxsplit=2)
    cmd = parts[0]
    if cmd not in PLAN_COMMANDS:
        return False, False, ""
    ...
```

返回三个值是有讲究的：`handled` 决定 REPL 要不要吞掉这行，`changed` 决定要不要立刻存档。两者分开，因为「`/skip 99` 这种报错」也算 handled（不该被当成新任务去规划），但没有改动（不该写盘）。

`/add` 特殊：标题允许带空格，所以整段取（`line[len(cmd):]`），不用 `split` 的第三段。

命令层的错误全部转成可读中文，一个异常都不往外抛：

```
/skip 99                 handled=True changed=False -> （没有编号为 99 的任务（共 3 个））
/skip abc                handled=True changed=False -> （任务编号要是数字，收到：'abc'）
/skip                    handled=True changed=False -> （/skip 需要任务编号，例如 /skip 2）
/edit 1                  handled=True changed=False -> （/edit 需要新标题，例如 /edit 1 新的任务描述）
```

### 2.6 改完立刻存档，并把阶段拉回来（第 210–230 行）

```python
if changed:
    edits.append(line)
    # 计划又有活了，把阶段从 done 拉回 executing，否则 /resume 会说「已完成」。
    phase = "done" if plan.is_complete else "executing"
    logger.log(
        "plan_edited",
        command=cmd,
        phase=phase,
        progress=plan.progress_text(),
        summary=plan.summary(),

    save_session(store, goal, phase, plan, messages, budget, logger.log)
```

两个细节：

- **立刻存档**：改完直接 `/exit`，再 `/resume` 回来还是改后的样子。不存盘的话，人做的调整就白做了。
- **阶段回拉**：V5 里计划完成时 `phase = "done"`，而 `load_resume` 遇到 `done` 会直接说「已经完成，不需要继续」。你 `/add` 一个任务，阶段却还是 `done`，`/resume` 就把你挡在门外。所以每次改动都重算一次 `phase`。

## 3. 值得记住的三件事

### ① 「谁能改计划」是权限问题，不是功能问题

`/skip`、`/add` 这些如果做在工具清单里，模型也能调——那 V5 辛苦建立的两道闸门就漏了一道：你批准的是 7 步，它执行到一半加一步，你只在报告里看到。

V6 的选择是：**改计划只能来自 REPL**。模型的工具集一个字没动，它仍然只能 `update_task` 改状态。

这也解释了为什么 V5 的 `Plan` 支持 `to_dict` 是必要的——如果计划只是一段文本，你根本没法「改第 4 条」，只能重写整段。

### ② 接管点是「轮次之间」，不是「随时」

REPL 是单线程的：`execution_phase` 里一旦开始调模型、跑工具，就阻塞在那里，你的 `/skip` 打不进去。

所以 V6 的接管窗口是**每次 `execution_phase` 返回之后**：模型停下来汇报、预算不够了、轮次转满了。这三个时刻 V5 都只是把控制权丢回给你，V6 让它变成有工具可用的时刻。

想做「随时中断」需要另一套东西：工具执行前检查一个队列、或者把 agent 放到后台线程。那是 V7 的活。

### ③ 保险丝要软着陆

V5 的坑是「硬停」：检查发生在每轮开头，冲爆了就停在半路，任务状态停在 `in_progress`，模型下次看到还以为是刚做的。

V6 的软着陆是**预估 + 提前收**：上一轮花了多少，下一轮大概也要这么多，不够就现在停。停之前一定 `save_session`，所以 `/go` 能接着做。

这两种停法的区别不在「会不会停」，在**停的时候现场是不是干净的**。一个停完能接着跑，一个停完要人猜。

## 4. 踩过的坑

### 坑 1：恢复出来的历史里有过期结论

就是 §2.4 那个。教训比「加一条消息」更普遍：**状态（`plan` / `budget`）和对话历史是两套东西，它们会不一致**。

- 计划说「任务 4 是 pending」，历史说「预算用完了，工具不执行」；
- 预算对象说「还剩 57000」，历史说「用完了」。

模型只能看见历史（再加上每轮的 system prompt），看不见你的 `Budget` 对象。所以每次「人工干预」，都要把**改了的事实**写成一条消息发进去，而不是只改内存。

### 坑 2：`/rm` 会让模型说旧编号

删除后重新编号 1..N，但历史里模型可能还在说「任务 6」。它下一轮会看到 system prompt 里的新计划，一般能自我修正；但如果它引用旧编号调 `update_task`，那就是一次工具报错（「没有编号为 6 的任务」）——错误信息会告诉它现有几个任务，它能改对。

另一种做法是保留编号空洞（删了 3 就永远没有 3）。好处是指针稳定，坏处是人看着别扭、模型也容易数错。V6 选了重编号，理由写在 `remove()` 的 docstring 里。**这种取舍没有标准答案，写下来就行。**

### 坑 3：改完不存盘，等于白改

第一版把 `save_session` 写在 `/go` 里。结果：`/skip 6` → `/exit` → `/resume`，任务 6 又回来了。

改计划是**人的操作**，它可能发生在任何时候（包括「我现在不想继续，先改一下明天再做」）。所以存档必须紧跟在改动后面，而不是等下一次执行。

```
  3. [pending] 生成 report.md
  4. [skipped] 最终复查（人工跳过）
  5. [pending] 补一份清单（人工新增）
进度：1/5 完成
分项： 4 pending / 1 skipped
```

### 5.2 边界

```
skip 已完成 -> 任务 1 已完成，跳过没有意义
retry 不存在的编号 -> 没有编号为 99 的任务（共 5 个）
rename 空标题 -> 任务标题不能为空
add 到 13 个 -> 计划最多 12 个任务，先删掉一个再添加
```

### 5.3 命令解析

```
/skip 2                  handled=True changed=True -> 任务 2 已跳过：b
/retry 2                 handled=True changed=True -> 任务 2 已打回 pending：b
/edit 2 改过的标题            handled=True changed=True -> 任务 2 已改名：改过的标题
/add 新任务 带空格             handled=True changed=True -> 已新增任务 4：新任务 带空格
/rm 1                    handled=True changed=True -> 已删除任务：a（后面的任务已重新编号）
/skip 99                 handled=True changed=False -> （没有编号为 99 的任务（共 3 个））
/skip abc                handled=True changed=False -> （任务编号要是数字，收到：'abc'）
```

### 5.4 没有计划时

```
你> /skip 1
（当前没有计划：先描述一个任务，或 /resume 恢复一个会话）
```

### 5.5 轮次上限

```
剩余 0 个任务 -> 上限 16
剩余 3 个任务 -> 上限 16
剩余 7 个任务 -> 上限 25
剩余 12 个任务 -> 上限 40
```

### 5.6 V5 回归

```powershell
uv run python src/v5_planner.py
你> /plan
你> /exit
```

V5 的输出（包括「还有 N 个任务未完成」那句）与提交时一致——新参数都有默认值，新文案只在 `soft_landing=True` 时生效。

## 7. V6 没做的事（留给以后）

- **执行中不能接管**：模型在跑的时候你打不进命令，只能等它停下（§3②）。
- **不能改目标**：`goal` 定了就是定了，改只能开新任务。
- **模型没有建议权**：它发现「还该做一步」只能嘴上说，不能提议加任务。
- **没有评测**：改完提示词、改完计划，好不好还是靠人看一次输出。
- **不能并行**：一次给 7 个工具调用，还是串行执行。
