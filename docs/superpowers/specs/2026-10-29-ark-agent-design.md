# 从零做一个 AI Agent —— 设计文档

日期：2026-10-29
作者：用户 + 助手
状态：待用户批准

---

## 1. 意图：为什么做这个

用户（下称「学员」）是 Java 背景的开发者，会写代码但没写过 Python，对 AI / Agent 开发属于入门阶段。
目标**不是**尽快得到一个成品工具，而是**通过亲手把一个小 agent 从小到大搭起来，建立对 agent 运行机制的直觉**，并在过程中做出一个能对话、能干活、能整理文件的个人助手雏形。

判据很简单：学员能指着任何一段代码说清「这段解决什么问题、去掉它会怎样」。如果只得到一个能跑但讲不清的黑盒，就算失败。

## 2. 目标 / 非目标 / 反目标

### 目标

1. 逐版递进，每版都是**可运行、可观察**的，且能清楚看到「这一版新增的 X 行解决了什么问题」。
2. 全程只用原生的 `fetch` 调模型 HTTP 接口，**不引入任何 agent 框架**（LangChain / CrewAI / Vercel AI SDK 等）。
3. 最终形态（V4）具备：多轮对话、工具调用、文件整理能力、操作前确认。
4. 学员能独立解释：消息格式、工具 schema、`tool_use` / `tool_result` 闭环、上下文累积、权限边界。

### 非目标（本阶段明确不做）

- 图形界面（CLI 即可；想做 Web 界面是后续独立项目）
- RAG / 向量库 / 知识库
- 多 agent 协作、任务编排框架
- 流式输出（作为 V4 之后的可选加分项）
- 打包发布、安装器、跨平台适配
- 完整的自动化测试体系（学习项目只需要冒烟验证 + 关键路径手测）

### 反目标（即使「技术上能跑」也算做坏了）

- 学员变成「配置工程师」：只会改配置、抄提示词，出问题无法定位。
- agent 变成一个不可解释的黑盒：日志不可读、失败原因不明。
- agent 拿到**无限制**的文件系统写权限，能误删或改动工作区之外的东西。
- 为了「像样」而提前堆架构：一上来就搭抽象层，导致前三天看不到 AI 的行为。

## 3. 约束（已通过实测确认）

### 3.1 运行环境

| 项 | 值 |
|---|---|
| OS | Windows（win32） |
| Python | **3.14.4**（由 uv 管理，不在系统 PATH 上）✅ |
| uv | 0.11.12 ✅（环境与运行入口） |
| Node | v22.14.0（已安装，本项目不使用） |
| git | 2.45.1 ✅ |
| 工作目录 | `D:\zjy\AI`（当前仅有 `docs\`） |

Python 不在 PATH 上的原因：`python.exe` 被 Microsoft Store 的占位程序占用。本项目全程用 `uv run`，绕开该问题，不修改系统 PATH。

### 3.2 模型接入（已实测，2026-10-29）

学员持有的 `ARK_API_KEY` 属于**火山方舟 Coding Plan**，可用性与常见文档不同，实测结论如下：

- ✅ 可用地址：`https://ark.cn-beijing.volces.com/api/coding/v1/messages`
- ❌ 不可用地址：`https://ark.cn-beijing.volces.com/api/v3/chat/completions`（返回 `InvalidEndpointOrModel.NotFound`）
- 协议：**Anthropic Messages API 格式**，不是 OpenAI Chat Completions 格式
- 请求头：`x-api-key: <key>`、`anthropic-version: 2023-06-01`、`content-type: application/json`
- 可用模型：`doubao-seed-2-1-pro`（另有别名 `claude-sonnet-4-5`，实际路由到 `doubao-seed-2-1-turbo-260628`）
- ✅ **已验证支持 function calling**：发送 `tools` 定义后，模型返回 `stop_reason: "tool_use"` 与 `{"type":"tool_use","id":...,"name":...,"input":{...}}`

**关键细节（容易踩坑，必须在 V1 就处理对）**：该模型的响应里含 `{"type":"thinking","thinking":...,"signature":...}` 块。多轮工具循环时，必须把 assistant 的 `content` 数组**原样**回填进下一轮 `messages`（含 thinking 块及其 signature），否则会报错或行为异常。

### 3.3 学员约束

- Python 没写过，但 Java 熟练 → 语言本身不是障碍：语法一周内可平，重点只讲 Python 与 Java 的差异（缩进即语法、动态类型、`dict`/`list` 对应 `Map`/`List`、`None` 对应 `null`）。
- AI / agent 零基础 → 专业术语首次出现必须解释，且优先用「去掉它会怎样」的方式说明其存在理由。
- 期望节奏：慢慢完善，不追求速度。

## 4. 候选方案与选择

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A. 分层递进** | V0 对话 → V1 单工具 → V2 多轮循环 → V3 文件整理 → V4 多工具助手，每版独立可跑 | 反馈最快、每步可解释；但前期「有用感」弱 | ✅ **已选** |
| B. 先读开源项目源码 | 挑成熟 agent 的核心文件逐行读懂后再写 | 结构视野快；但缺部件存在理由的直觉，易变成照抄 | 否 |
| C. 先搭骨架再填能力 | 先建配置层/日志层/工具注册表/会话存储 | 结构干净、贴合 Java 习惯；但前两天看不到 AI 行为，反馈慢 | 否 |

**选择理由**：学员当前的瓶颈是「没见过 agent 动起来」，而非设计能力。A 能在第一天就让学员亲眼验证「模型自己决定去调工具」，这是后续所有理解的锚点。C 的骨架在 V3 会自然需要，那时引入才知道每一层为何存在。

## 5. 已定的「怎么建」

### 5.1 技术栈（我的决定，课程中可调整）

- Python 3.14 + **uv** 管理解释器、虚拟环境与依赖；**不配置打包/构建流程**。
- 依赖策略：**只装 `requests`**（一个 HTTP 库），其余全用标准库（`json`、`pathlib`、`os`、`sys`）。
- 学员侧只有两条命令：`uv add requests`（装依赖，一次性）、`uv run python src/v0_chat.py`（跑）。
- **不装**：`openai` / `anthropic` 官方 SDK、LangChain 等框架、pytest。

为什么用 `uv` 而不是 `pip`：本机 `python` 命令被 Microsoft Store 占位程序占用，`pip` 也不可用；`uv` 已经装好且能自己管理解释器，一条命令就能跑，不必改系统环境变量。

### 5.2 目录结构

```
D:\zjy\AI\
  pyproject.toml        # uv 管理，声明 requests 依赖
  .python-version       # 3.14
  .env.example          # 提交；说明需要 ARK_API_KEY
  .env                  # 不提交；从系统环境变量取，禁止硬编码
  .gitignore            # 忽略 .venv\ .env workspace 产物
  src\
    v0_chat.py          # 单轮对话，独立文件
    v1_tool.py          # 单工具调用，独立文件
    v2_loop.py          # 多轮 REPL + 循环，引入 agent\
    v3_files.py         # 文件整理，引入沙箱与确认
    v4_assistant.py     # 收口版
    agent\
      client.py         # 唯一的模型调用封装（含 thinking 回填、超时、重试）
      tools.py          # 工具注册表 + JSON Schema 定义
      sandbox.py        # 路径校验（V3 起）
  workspace\            # agent 唯一被允许改动的目录（沙箱）
  docs\
    superpowers\specs\  # 本文件
    notes\              # v0.md ~ v4.md：每版讲「新增了什么、为什么、去掉会怎样」
```

**刻意保留的重复**：V0 / V1 各自独立单文件，不复用 `agent\` 包。学员可以两份并排对照，看清「加了工具之后多了哪几块」。V2 起再抽公共模块——此时抽象是被需求逼出来的，不是提前设计的。

### 5.3 各版本内容

| 版本 | 规模 | 新增能力 | 要讲清的核心概念 |
|---|---|---|---|
| V0 | ~40 行 | 一次问答 | HTTP 请求结构、`messages` 数组、`system`、token 用量、为什么「模型没有记忆」 |
| V1 | ~100 行 | 一个工具的调用闭环 | JSON Schema、`tools` 定义、`stop_reason=tool_use`、`tool_result` 回填、thinking 块原样回填 |
| V2 | ~160 行 | 多轮 REPL + 循环 | 对话历史累积、循环终止条件（`MAX_ITERATIONS`）、上下文膨胀、`/clear`、错误重试 |
| V3 | ~240 行 | 文件整理（`list_dir` / `read_file` / `move_file` / `mkdir`） | 沙箱与路径校验、写操作前交互确认、dry-run、为什么「危险工具要有人把关」 |
| V4 | ~320 行 | 多工具 + 简单任务规划 | 工具选择策略、system prompt 如何影响规划、日志与可观测性、成本控制 |

规模为估算，用于判断「一天能不能啃下来」，不作为验收标准。

### 5.4 安全边界（不可协商）

1. 文件类工具只允许操作 `D:\zjy\AI\workspace` 之下；路径先 `path.resolve` 再校验前缀，拒绝 `..` 逃逸与符号链接穿透。
2. 一切写操作（move / mkdir / 覆盖）默认 **dry-run 打印计划**，需用户输入 `y` 才执行。
3. `run_shell` 类工具**本阶段不提供**。若后续加，必须单独设计白名单。
4. API key 只从 `process.env.ARK_API_KEY` 读取，任何文件里不得出现明文 key。

### 5.5 验证方式（学习项目尺度）

- 每版一个可复现的手测脚本（写在 `docs\notes\vN.md` 里）：一条命令 + 期望输出。
- V1 起保留 `uv run python src/smoke.py`，做 3~5 行的冒烟调用，确认接口没挂。
- 不做单元测试框架；不追求覆盖率。

### 5.6 节奏

按「一次会话吃一版」推进：每版先讲清目标与新概念（10 分钟）→ 助手写出该版代码 → 逐块讲解 → 跑通 → 学员复述「这一版多了什么」。
预估 V0–V2 约 3 次会话，V3–V4 约 2–3 次会话。学员随时可以喊停或要求放慢。

**逐版滚动交付**：每版跑通并经学员复述确认后，才开始下一版。不一次性产出 V0–V4。

### 5.7 分工与交付方式

**代码由助手编写，学员负责读、跑、问、复述。**（学员已明确选择）

- 助手交付：该版本完整可运行的代码 + 逐行/逐块讲解 + `docs/notes/vN.md` 讲义。
- 学员交付：跑通、复述「这一版新增了什么、去掉会怎样」、提出看不懂的地方。
- 每版附 2–3 个「改一改试试」的小任务（例如把 `max_iterations` 改成 1 看会发生什么），成本极低但能建立因果感；**做不做自愿**。
- 学员不要求自己从零敲，但鼓励动手改数值、改提示词、删一行看报错——这是成本最低的理解方式。

### 5.8 已定的教学决策（助手拍板，学员可否决）

| 决策 | 结论 | 理由 |
|---|---|---|
| 交付节奏 | 逐版滚动，每版跑通再往下 | 保证「每步都懂」，避免一次给五版造成消化不良 |
| 规模数字含义 | 只算代码行，不含注释；每行注释只答「为什么」，长篇讲解放 `notes/` | 保持「这一版多了哪几块」的横向可比性 |
| 失败演示 | 每版安排一次故意失败（工具名写错 / 路径越界 / 循环打转 / 超迭代上限） | 「能定位问题」是反目标里明确要求的，只能靠亲手见过错误来训练 |
| `notes/` 定位 | 讲义式，末尾 3 个复述题 + 自检清单 | 直接服务于「能指着代码说清」这一验收判据 |
| V4 的「规划」 | 先用 system prompt 驱动多步工具调用，不引入显式 plan 数据结构 | 显式 plan 属 V5；提前做会踩中「不提前堆架构」的反目标 |

## 6. 留给 builder（实现者）决定的

以下问题不影响「做什么」，由实现时按当时的判断定，不阻塞开工：

- 具体提示词措辞（`system` 内容随版本演进，按需调整）
- `MAX_ITERATIONS` 的默认值（先取 8）
- 日志格式（先简单 `print`，V4 再统一）
- 是否给 V1 的工具选 `read_file` 还是 `list_dir`（倾向 `list_dir`：结果直观、风险为零）
- 是否给函数加类型标注（倾向加轻量标注，如 `def read_file(path: str) -> str`，便于与 Java 的签名对照）
- 交互输入用 `input()` 还是 `argparse`（倾向 `input()` 的 REPL，V2 起再考虑参数）
- 是否 `git init` 并逐版提交（倾向做：`git diff` 能直观看到「这一版多了哪几行」）
